# 解题说明 · ReAct 循环

## 为什么这层值得单独考

模型侧的「能力」不可判，运行时侧的「协议」却极其可判：输入是固定文本，输出是固定元组。生产中出事最多的也正是这层——解析器没认出新格式、工具名幻觉导致崩掉、循环跑到 `max_steps` 才停、`Observation` 拼错位置让模型反复做同一件事。把它写成纯函数之后，所有边界都能用几个断言钉住。

## 终止条件是四种，不是一种

1. 模型给出 `Final Answer`（正常收手）；
2. 某一轮既没有 Action 也没有答案——模型在「想」但不再行动，继续循环只会空转；
3. 连续两轮 `(工具名, 参数)` 完全相同——这不是进展，是死循环；
4. `max_steps` 用尽或脚本提前耗尽——外部兜底。

只实现第 1 与第 4 种是常见写法，结果是「模型忘记输出 Action」时白白烧完预算。第 3 种比较微妙：`(name, input)` 必须两段都相同才算重复，同一工具换个参数是正常的多轮调查。

## 解析比看起来难

- **冒号后的空白**：`Action Input: Beijing` 与 `Action Input:Beijing` 都要得到 `Beijing`，所以要 `split` + `strip`，不能用固定列切片。
- **大小写**：模型偶尔吐 `action:`，协议匹配应不区分大小写（本题统一按小写比较）。
- **同一轮的干扰行**：`Thought` 里可能引用「Action: 应该是 weather」这样的示例文本。按「行首前缀」判断可以挡掉绝大多数误判，这也是真实实现的做法。
- **`Action` 没有 `Action Input`**：真实框架会直接报错并让上层重试，本题按 `ValueError` 处理——静默当成空参数会让工具收到 `""`，事故更难查。

## 未知工具与死循环护栏

两者都是「让 agent 自己纠正」而不是「让运行时崩掉」的设计：错误观测返回给模型，下一轮它往往就能改对。区别是护栏的判定发生在执行**之前**——重复动作不再真的调用工具（可能带副作用，比如重复下单），只记一次。

## steps 的口径

`steps` 统计的是「消费了几轮模型输出」，所以：

- 一轮就给出答案 → `steps == 1`、观测为空；
- 第 2 轮触发重复护栏 → `steps == 2`，但工具只被调用 1 次；
- `max_steps == 0` → 一轮都不消费，用来做「预算耗尽后是否还能直接回答」的测试。
