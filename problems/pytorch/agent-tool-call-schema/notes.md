# 解题说明 · 工具参数校验

## 为什么值得单独写

这层代码的失败模式非常统一：要么「太松」（`"3"` 一路传到 `range()` 里炸在几百行之外），要么「太紧」（模型少写一个可选字段就整轮重试）。生产里调的都是同一组旋钮：哪些类型可以兜、默认值补不补、多余字段是报错还是丢弃。把它写成纯函数，这组旋钮就变成可测的用例。

## 校验顺序决定错误信息

三类问题会同时出现：字段缺失、类型不对、多余字段。如果按「遍历 arguments」来报错，同一个输入在不同字典序下会给出不同顺序的错误列表，重试时模型看到的信息也跟着抖。所以固定成：

1. `required` 缺失（按 `required` 列表顺序）；
2. 已出现的字段（按 `properties` 的插入顺序，嵌套错误逐层拼路径）；
3. 多余字段（按 `arguments` 的插入顺序）。

也就是说「schema 的形状」决定错误顺序，「参数的形状」只在多余字段那一档起作用。

## 可兜与不可兜

- **可兜**：`integer` 收到 `3.0`。JSON 没有整数/浮点之分，`3.0` 与 `3` 在线上是同一个东西，归一回 `int` 反而是修复。
- **不可兜**：`"3"` 收到 `integer`。它能被 `int()` 强转，但强转失败率极高（`"3.0"`、`"3kg"`、`"三"`），静默转换会把错误藏起来。
- **必须拒绝**：`bool` 收到 `integer`。Python 里 `True == 1`，谁先用 `isinstance` 谁就把「开关」当成了「数量」，这是最经典的线上事故。

## 枚举的坑：`==` 不够

`enum=[0, 1]` 配上 `True`，只比 `==` 会判定命中。JSON Schema 的语义是「值必须等于枚举里的某一项，且类型相容」，所以实现里要 `type(item) is type(value) and item == value`。同理 `number` 归一成 `float` 之后，`0.0` 也不再命中 `[0, 1]` 这两个 `int`——这条看起来苛刻，但它让「枚举是整数字面量」的语义变得明确。

## 默认值的两个细节

- **非必填字段缺了就补**，这样下游函数不必到处写 `args.get("k", 1)`；
- **必填字段带 `default` 时按补齐处理**：真实 schema 里这属于「写错了」，但既然给了默认值，运行时兜住比让整轮重试划算。
