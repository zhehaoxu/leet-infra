# 解题说明 · cache-aware 路由

## 两个项的量纲要先统一

`alpha * 未命中块数 + beta * 队列深度` 里，前一项是「块」，后一项是「请求数」。这不是物理量纲一致，而是刻意选的**代价货币**：`alpha / beta` 就是「多等一个请求」和「多算一块 prefill」之间的汇率。调参时只需要动这个比值，不用动绝对大小，理解这一点比记住公式更有用。

## 前缀命中为什么要「断掉就停」

分页前缀缓存复用的一定是**从 token 0 开始的连续块**。如果实现成「请求里有多少块在缓存里」，那么 `[10, 99, 11]` 在 `{10, 11}` 上会被算成命中 2 块，可实际上第一块 99 就断了，第 3 块 11 前面没有可复用的 KV，根本没法跳过。这类题的正确写法只有一个循环：

```
k = 0
while k < len(blocks) and blocks[k] in cache: k += 1
```

## 状态必须推进，否则就是一次性决策

路由完之后要做两件事：`queue[chosen] += 1` 和把请求的**全部**块写进该副本的缓存（不只是命中的那部分）。漏掉写回，第二个同前缀请求会重新按「谁都没有」去比，粘性就没了；漏掉队列加一，负载项永远是初始值，`beta` 形同虚设。

## 两种极端是天然的断言

- `alpha = 0`：代价只剩队列，等价于「最少连接」负载均衡，选出来的副本号会按队列深度轮转。
- `beta = 0`：代价只剩未命中块数，等价于「缓存优先」，粘住第一个命中的副本不放。

这两条既是对实现的自检，也是理解参数意义的入口。

## 为什么并列要显式规定

`alpha = beta = 0` 时所有代价都是 0，若不定「并列取小副本号」，结果就依赖遍历顺序或浮点比较细节。工程上这类并列并不罕见（比如初始状态两个副本都没缓存、队列都为空），所以必须写死。

## 复杂度

M 个请求 × R 个副本 × 每行最多 L 块：O(M · R · L)。真实路由是微秒级路径，缓存命中数会预计算成哈希表，但判定口径不变。
