# 题解：NCCL 启发的校准代价表选择

## 1. 先理解校准值，再统一单位

按行展开校准表：先 Ring，后 Tree；每行依次为 LL、LL128、Simple。这样自然得到规定的候选编号，不需要按算法写额外分支。算法名称和协议名称不隐含额外系数：输入已经表示目标环境下的有效启动延迟与算法带宽。

十进制带宽 \(B\) GB/s 等于 \(B\cdot10^9\) 字节/秒，因此传输 \(S\) 字节需要

\[
 \frac{S}{B\cdot10^9}\cdot10^6=\frac{S}{1000B}
\]

微秒。加上启动延迟，得到 \(t(S)=\alpha+\beta S\)，其中 \(\beta=1/(1000B)\)。不要将 1000 换成 1024，不要乘以八，也不要再加 Ring/Tree 通信系数。尤其不能把算法带宽自动视为总线带宽。

## 2. 直接比较所有直线，得到下包络

对每条消息计算六种方案的耗时，再选择最小值。按编号顺序扫描，只有出现严格更小的耗时才更新赢家，即可稳定处理平局。Python 对有序编号使用 `min` 也有相同行为。赢家比较不使用容差：即使只慢一点，也不能因为编号更小而获胜。

赢家位于全部代价直线的下包络上。无需排序消息，也不应假定协议总是按 LL、LL128、Simple 的顺序切换，更不必使用两两阈值派发消息。给定校准表可以让任意候选方案获胜。

## 3. 单独推导两两交点

令两条直线的耗时相等：

\[
 (\beta_i-\beta_j)S=\alpha_j-\alpha_i.
\]

带宽相等时，斜率也相等。截距不同意味着没有交点；截距相同意味着处处重合。这两种情况都没有唯一阈值，因此均为 `None`。同一候选方案对应的对角线也为 `None`。

带宽不等时，求实数交点，仅保留非负值。斜率差可以改写为

\[
 \beta_i-\beta_j=\frac{B_j-B_i}{1000B_iB_j},
\]

避免直接相减两个接近的倒数。参考实现使用这一等价形式。不要用 epsilon 将接近的带宽判为相等，它们可能对应很大的有效阈值。每个无序候选对只计算一次，再同时填入两个对称位置。必要时将带符号的零规范化为零；分数字节交点不能取整。

交点仅表示两条直线相等。示例中的候选 0 和 2 在 8000 字节处相交，耗时都是 9 微秒，但候选 1 只需 8 微秒。真正的最优区间是：不超过 6000 字节时选 0；超过 6000 且不超过 12000 字节时选 1；超过 12000 字节时选 2。边界归属由编号平局规则决定，与 Ring 或 Tree 的名称无关。

## 4. 推导并解释吞吐率指标

确定赢家 \(w\) 后，必须使用包含启动延迟的完整耗时：

\[
 A=\frac{S}{1000t_w},\qquad
 U=\frac{A}{B_w}=\frac{S}{1000\alpha_w B_w+S}.
\]

启动延迟为正，因此有限大小消息的精确模型利用率小于一，零字节消息的利用率为零。固定某一候选方案时，消息增大，其吞吐率逐渐逼近校准带宽。浮点舍入可能使利用率在数值上等于一。这些指标没有计入其他流量、链路编码或 collective 总线流量放大，不能当作实测硬件利用率。

## 5. 边界与验证思路

- 零字节消息只比较延迟。赢家耗时仍为正，因此两项吞吐率计算均可安全得到零。
- 延迟相同、带宽不同的候选方案在零处相交；这是有效阈值，不是 `None`。
- 负交点位于消息大小定义域之外，应丢弃。平行线与重合线也没有唯一可报告的交点。
- 空消息序列仍需计算由校准表决定的阈值矩阵，其余结果为空。重复或乱序消息保持原位置。
- 测试使用 `Fraction` 对整数和二进制分数样本做精确计算，并通过独立的交叉相乘方程核对交点；还将返回交点代回两条耗时直线，检查对称性、六种获胜编号、近似平局与精确平局的区别，以及真正下包络切换点前后的赢家。
- 消息字节数与带宽同时乘以同一因子，耗时和赢家应保持不变，吞吐率及字节阈值按该因子缩放，利用率不变。这可以发现十进制单位错误或隐藏的算法系数。

## 6. 复杂度

设消息数为 \(N\)、候选数为 \(K\)，时间复杂度为 \(O(NK+K^2)\)。必要输出占用 \(O(NK+K^2)\) 空间，输出之外的辅助空间为 \(O(K)\)。本题 \(K=6\)，因此总时间与输出空间均为 \(O(N+1)\)，辅助空间为常数。无需硬件访问或第三方库。

## 7. 与 NCCL 上游的联系及限制

已核实的上游依据为 [NVIDIA NCCL v2.23.4-1 的 `src/graph/tuning.cc`](https://github.com/NVIDIA/nccl/blob/v2.23.4-1/src/graph/tuning.cc)。该版本的 `ncclTopoGetAlgoTime` 读取延迟、带宽表项，最终使用：

```cpp
*time = lat * latCount + nBytes / (1000 * bw);
```

文件明确注明延迟单位为微秒、带宽单位为 GB/s。函数还处理带宽不可用、Ring 后备带宽、Tree AllReduce 大小修正、多节点 Ring-Simple 延迟修正，以及与聚合有关的延迟计数。本题只借鉴“延迟加传输时间”的结构：有效延迟吸收目标场景中的启动影响，直接使用给定的算法带宽。

这里没有通用硬件常数，示例也不是硬件基准测试。真实 NCCL 还有更多算法、可用性规则，以及随版本变化的调优逻辑。固定六候选的教学模型并不复刻 NCCL 的完整选择器，也不能证明哪种实现会在某台机器上实际最快。
