# NCCL 算法与协议：代价表选择及交叉阈值

## 基于校准表选择通信方案

通信方案需要权衡启动延迟与持续带宽：小消息可能更适合低延迟方案，大消息则可能更适合高带宽方案。候选方案的编号固定为：

**0：Ring-LL · 1：Ring-LL128 · 2：Ring-Simple · 3：Tree-LL · 4：Tree-LL128 · 5：Tree-Simple。**

使用给定的校准表，而不是与硬件无关的固定常数。各候选方案的有效延迟 \(\alpha_i\) 和算法带宽 \(B_i\) 已经包含拓扑、world size 的影响，**不要**额外乘以 Ring 通信步数、Tree 深度或其他算法系数。

对于大小为 \(S\) 字节的消息，模型耗时以微秒计：

\[
 t_i(S)=\alpha_i+\frac{S}{1000B_i}.
\]

带宽使用**十进制 GB/s**，不是 GiB/s，也不是 Gbit/s。记录所有候选方案的耗时并选择最小者；耗时完全相等时选编号最小者。保持消息的原始顺序。

## 两两交点与吞吐率

令 \(\beta_i=1/(1000B_i)\)。对于斜率不同的候选方案，求解等耗时方程：

\[
 S_{ij}=\frac{\alpha_j-\alpha_i}{\beta_i-\beta_j}.
\]

保留非负实数交点，不要取整为整数字节。交点为负、直线平行或重合、以及对角线位置均记为 `None`。交点表应当对称。即使消息序列为空，也需要计算交点表。

两条直线的交点**不一定是全局最优方案的切换点**：第三个候选方案可能同时优于二者。真正的赢家由六条代价直线的下包络决定。

对于获胜方案 \(w\)，计算有效吞吐率及利用率：

\[
 A(S)=\frac{S}{1000t_w(S)},\qquad U(S)=\frac{A(S)}{B_w}.
\]

它们分别表示模型中的有效载荷吞吐率及其占所选算法带宽的比例，不是物理链路利用率。消息为零字节时，仅比较启动延迟；吞吐率与利用率均为零。

## 示例

以下数字仅为演示用校准值，不是通用硬件测量结果。

```python
message_sizes = [0, 8000, 16000]
latencies_us = [[1.0, 4.0, 7.0], [4.0, 7.0, 10.0]]
bandwidths_gbps = [[1.0, 2.0, 4.0], [1.0, 2.0, 4.0]]
```

## 适用范围与上游依据

本题是 **NCCL 启发的教学用校准 alpha-beta 模型**，不是对真实 NCCL 选择逻辑的复刻，也不能保证预测其实际行为。已核实的 [NCCL v2.23.4-1 `ncclTopoGetAlgoTime` 源码](https://github.com/NVIDIA/nccl/blob/v2.23.4-1/src/graph/tuning.cc) 使用 `lat * latCount + nBytes / (1000 * bw)`，延迟单位为微秒、带宽单位为 GB/s。上游还会根据 collective、消息大小、拓扑和流水线等因素进行修正。本题有意用给定的有效校准值替代这些细节，并在各消息之间保持该表不变。无需 GPU、NCCL 安装或新增依赖；具体数据约定见 starter。
