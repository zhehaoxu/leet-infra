# 解题说明 · 上下文预算压缩

## 压缩的本质是「带钉住约束的背包」

每条片段有重量（token）与价值（优先级），窗口是容量。0/1 背包是 NP-hard，但生产系统不会去解精确解：优先级就是人给定的价值序，贪心足够好且可解释。真正要保证的是**确定性**——同样的输入必须得到同样的保留集合，否则复现线上问题就无从谈起。

钉住片段相当于「必须入包」的约束：先扣掉它们的重量，剩下的做普通贪心；如果连它们都装不下，说明配置本身错了（窗口太小或 system prompt 太长），必须报错而不是悄悄降级。

## 为什么「跳过不是终止」

新手实现常见两种：

- `break`：遇到第一个装不下的就以为「后面的更装不下」——但排序是按优先级，不是按大小，后面的小片段完全可能装进去；
- 无限循环：装不下就跳过但忘记推进游标。

正确做法是按优先级遍历一遍，装得下就放入、装不下就略过，`used` 单调不减，一趟 O(n log n)（排序主导）。

## 为什么返回时间序

拼 prompt 时片段必须按对话时间排列：system 在最前、历史居中、scratchpad 在末尾。如果按优先级顺序拼，模型会看到「结论在证据之前」的乱序上下文，效果比丢片段更差。所以挑选用优先级、输出用原始下标。

## 真实系统里更多的旋钮

- **recency 加成**：越近的片段越可能被保留，通常实现成 `priority + k / age`；
- **摘要位**：压缩掉的中段不是直接消失，而是换成一段「已摘要」占位符（会额外消耗固定 token）；
- **成对约束**：`tool_call` 与 `tool_result` 必须同进同出，否则协议直接非法；
- **token 估算误差**：离线用 tokenizer 计数，线上常用启发式估算，所以要留安全边际。

本题只保留「钉住 + 优先级 + 预算」这条主干，正是因为它最可判、也最容易出事故。
