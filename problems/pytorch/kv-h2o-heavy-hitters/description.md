# KV Cache：H2O 累计注意力与重击手池

## 题目描述

**H2O**（Heavy-Hitter Oracle, Zhang et al., NeurIPS 2023, arXiv:2306.14048）观察到一个经验规律：解码过程中，少数 token 承担了绝大部分注意力质量，且这批「重击手」在步与步之间高度稳定。于是它把 KV 缓存压缩成「**sink + 累计 top-k**」：

- **sink**：序列最前面的若干 token（BOS、指令前缀）几乎被每一步持续关注，属结构性必需，无条件保留；
- **重击手**：把**每一步的注意力分数按列累加**，累加值最高的 token 就是重击手。

关键在「累加」的语义。给定一步的注意力行 \(a_s\in\mathbb R^{L}\)（已经对 head 与 query 求和），H2O 维护

\[
\text{acc}_s[j]=\sum_{t=0}^{s} a_t[j]
\]

**不做任何归一化**——既不除已见步数，也不对行做 softmax 之外的再缩放。第 \(s\) 步的保留集是

\[
\mathcal K_s=\{\,j<\text{sink}\,\}\ \cup\ \operatorname{top\text{-}k}\big(\text{acc}_s[0:P+s]\big)
\]

其中 \(P\) 是 prompt 长度、\(P+s\) 是第 \(s\) 步可以看到的列数（当步新生成的 token 尚未被注意，所以它的累计分恒为 \(0\)）。历史越久，被反复关注的 token 累计分越高，重击手因此「越用越稳」。

本题只要求输出**每一步的选择掩码轨迹**，不模拟物理上的缓存搬移/下标压缩。

## 任务

实现 `solve(attn, budget, n_sink)`：

- 输入：`attn`（float32 `(S, L)`，`S` 步、`L = P + S` 为最终缓存长度；第 `s` 行只有前 `P+s` 列有效，其余为 0）；`budget`（非负整数，重击手名额）；`n_sink`（sink 个数）。
- 输出 `(acc, keep)`：`acc` 为 `(L,)` float32（全程累计列和）；`keep` 为 `(S, L)` bool（第 `s` 行为第 `s` 步的保留掩码）。
- 第 `s` 步的候选列是 `[0, P+s)`；其中 `j < n_sink` 无条件保留，其余按 `acc_s` 降序取前 `budget` 个。
- **并列取小下标**（`acc_s` 相等时保留 index 更小的）。

**约定**：内部用 float64 累加、输出 float32；`budget` / `n_sink` 为整数。`budget < 0` 或 `n_sink ∉ [0, L]` 抛 `ValueError`。

## 示例

```
L = 6，S = 2（P = 4），budget = 2，n_sink = 1
attn[0, :4] = [0.10, 0.50, 0.20, 0.20]
attn[1, :5] = [0.05, 0.10, 0.25, 0.30, 0.30]

acc = [0.15, 0.60, 0.45, 0.50, 0.30, 0.00]      # 末列无人关注，恒 0
第 0 步：有效列 0..3，非 sink 分 [0.50, 0.20, 0.20] → 取 1、2（并列取小）
         keep[0] = [T, T, T, F, F, F]
第 1 步：有效列 0..4，非 sink 分 [0.60, 0.45, 0.50, 0.30] → 取 1、3
         keep[1] = [T, T, F, T, F, F]
```

## 约束

- `acc` 必须与「逐行累加、不除步数」一致：`S` 步全 1 时前 `P` 列累计为 `S`（取平均会得到 1）。
- 当步新 token 自身的累计分恒为 0，但随步数增长它会在后续步因被关注而进入候选。
- 每步保留数恰为 `n_sink + min(budget, P+s-n_sink)`（不足时有多少取多少）。
- 不得用 `torch.topk` 的未定义并列行为代替「并列取小下标」的约定。
