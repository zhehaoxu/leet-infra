# Deep dive: Async rollout admission, partial truncation and staleness accounting

## Origin
- **Async / partial-rollout RLHF serving**: AReaL (Infinite Light + Tsinghua, arXiv id pending source verification) treats "samples are always off-policy" as a first-class object — the training side keeps updating weights, the generation side never stops accepting work, and every in-flight request carries a **staleness cap**, so generation is interrupted at the deadline and a half-finished rollout is delivered (partial rollout). verl's (ByteDance, Seed) async / one-step-off-policy path and OpenRLHF's async vLLM generation server are the same mechanism under another parameterization: their `max staleness` / `partial rollout` knobs (exact field names pending source verification) are precisely this problem's $S$. The problem **depends on none of these libraries** (they are not in the judge environment either); it only distills the scheduling into one pure integer event table.
- **The off-policyness metric**: $\mu=\text{consumption version }c-\text{entry version }v0$, i.e. how many updates separate "the policy in force when this sample **started**" from "the policy in force when it was **eaten by training**". Some papers define it as "how many weight syncs happened while it was generating", which differs from this problem's $c-v0$ only by an off-by-one in "whether to count the current step"; here we follow the statement throughout: **entry version $v0=\lfloor start/st\rfloor$ from the start time, consumption version $c=\lfloor ready/st\rfloor$ from the whole batch's ready time**.
- **Abstraction gap vs real systems**: in a real system $st$ is a training step's wall-clock and a partial rollout resumes across several weight syncs; here all of that is compressed onto one integer time grid, token count = time unit, no randomness, no model forward.

## Full derivation and index conventions
1. **Slot recursion (the admission core)**: maintain $C$ equivalent slots' next-free times `release[0..C-1]`, initialized to $0$. Process requests in ascending $(\text{arrivals},i)$ order. For request $i$:
   - pick $j^\star=\arg\min_j \text{release}[j]$ (**ties → smallest slot id**),
   - $\text{start}_i=\max(\text{arrivals}_i,\ \text{release}[j^\star])$,
   - compute $\text{finish}_i$ (see below) then set $\text{release}[j^\star]\leftarrow \text{finish}_i$.
   This is exactly "the earliest-free slot takes the next request", the same root as `inf-continuous-batching-scheduler`'s continuous batching. Because the slots are equivalent, which tied slot you pick affects **no output** (it only relabels the intermediate `release`; there is no slot id in the outputs).
2. **Version grid**: version $v$ is in force only on the half-open interval $[v\cdot st,(v+1)\cdot st)$. $\lfloor t/st\rfloor$ is "which cell $t$ falls in", the sole source of every "version" index here. The grid is **publish**-driven and independent of whether the buffer has goods: the trainer advances it even with no data (idling).
3. **Why the deadline is pinned to the entry version $v0$, not the current version**: partial rollout means "this sample may cross at most $S$ versions before delivery". It starts inside cell $v0$, so its hard deadline is the left endpoint $S$ cells after $v0$: $\text{deadline}=(v0+S)\cdot st$. Pinning the deadline to "the current version" would make it slide and allow unbounded continued generation, losing the staleness bound — so once fixed against the entry time it never moves. From $S\ge1$ and $0\le start-v0\cdot st\le st-1$ we get $\text{deadline}\ge start+1$; combined with $\text{finish}=\min(start+\text{gen\_len},\text{deadline})$ and $\text{gen\_len}\ge1$ this gives $\text{finish}\ge start+1$ always (no zero-length requests).
4. **Completion and truncation**: $\text{finish}_i=\min(\text{start}_i+\text{gen\_len}_i,\ \text{deadline}_i)$; $\text{truncated}_i=[\text{finish}_i<\text{start}_i+\text{gen\_len}_i]$. Note it is **strictly less than** that counts as truncation — finishing exactly on the deadline ($\text{gen\_len}$ exactly fills the remaining window) does not.
5. **Batching by completion order (consumption side)**: queue requests in ascending $(\text{finish},i)$; the request at rank $q$ goes to $\text{batch\_id}=\lfloor q/B\rfloor$. The batch's availability is the **latest finish in the batch** (short-plank effect: $\text{ready}_k=\max_{i\in k}\text{finish}_i$), so $\text{consume}_k=\lfloor \text{ready}_k/st\rfloor$ is dragged back by the batch's longest member. $c$ is shared by the whole batch, so short samples "go along for the ride" and get stale next to long ones.
6. **Staleness and idle**: $\text{mu}_i=\text{consume}_{\text{batch\_id}[i]}-v0_i$. Idle $\text{stall}_k=\max(0,(\text{consume}_k-k)\cdot st)$ — under an ideal pipeline batch $k$ should be eaten at version $k$ (consumption version $=k$); falling behind gives $\text{consume}_k>k$ and a positive stall, over-supply is clamped to $0$ (the grid never moves backwards). The gap $(c_k-k)$, "consumption version − ideal version", measures **how many steps generation lagged behind training**.

## Core points and easy mistakes
- **Tied slots take the smallest slot id**: when several slots free at the earliest time simultaneously, pick the smallest id. Since slots are equivalent this only pins the intermediate state and does not change the final five-tuple; but writing "take any of them" makes the time-stepping oracle and the per-request reference solution disagree on the **intermediate table** (the easiest thing to misread as a bug while debugging).
- **Finishing exactly on the deadline is not truncation**: the test is the strict inequality $\text{finish}<\text{start}+\text{gen\_len}$. Counting $=$ as truncation is the #1 error (in the example, request 3's $7+5=12=\text{deadline}$ is exactly this boundary, `truncated=0`). The converse "one unit over must truncate" is the `[9]` case in `check_partial_rollout_trims_long_tail`.
- **Occupancy uses the half-open interval $[\text{start},\text{finish})$**: $\text{occupancy}[\tau]=\#\{i:\text{start}_i\le\tau<\text{finish}_i\}$, length $=\max_i\text{finish}_i$ (endpoint excluded). Writing a closed interval over-counts each request's last cell by one and breaks $\sum\text{occupancy}=$ total busy time. Self-check: `check_invariants` asserts `occ.sum() == Σ(finish-start)`.
- **stall length is $\lceil N/B\rceil$**: the batch count rounds up and the last batch may hold fewer than $B$. Using $\lfloor N/B\rfloor$ drops the final ragged batch entirely. `check_single_batch_when_batch_size_ge_n` and `check_matches_oracle_batch_size_sweep` pin this down.
- **The $N=0$ empty-tensor convention**: all five outputs are **empty int64 tensors of length $0$** (`occupancy`/`stall` are NOT length-1 zero vectors). And they must be `.to(torch.long)` — an empty tensor defaults to float, and `torch.equal` fails on the dtype mismatch.
- **Change $S$, move everything**: truncation rewrites finish ⇒ completion order changes ⇒ rank-based batching changes ⇒ $\mu$/stall/occupancy all change (request 2 is in batch 0 at $S=2$ but moves to batch 1 at $S=10$). So $S$ is not merely a truncation threshold; it is a knob that **feeds back into the whole timeline**.
- **A truncated sample always has $\text{mu}\ge S$**: a truncated sample is delivered at $\text{deadline}=(v0+S)st$ or at a later batch ready, hence $\text{consume}\ge v0+S$. (Do not flip the inequality direction.)

## How it differs from neighbouring problems
- **vs `inf-continuous-batching-scheduler`**: its `solve(requests, max_batch_size)` takes an $(N,2)$ array of `[arrival_step, gen_len]`, runs FCFS continuous batching once, and its **only output is each request's finish time** `finish (N,)`. It is an **inference-serving** view: a fixed concurrency cap, a request leaves as soon as it finishes, **no policy-version axis**, no deadline, no consumption-side batching. This problem **reuses its admission core** (earliest-free slot + `start=max(arrival, free)`) but adds three things: ① finish is **trimmed by a deadline derived from the entry version** and fed back into the timeline (partial rollout), ② requests are **batched by $(\text{finish},i)$ rank with a consumption version shared across the whole batch**, ③ it outputs **staleness mu, occupancy timeline, and idle stall**. Also, here `arrivals` is explicitly unordered with request-id tie-breaks, and `capacity` counts equivalent concurrent slots rather than a "max running batch".
- **vs `perf-kernel-launch-timeline`**: that one is also a "busy/idle" ledger, but over **kernel launches on a single serial stream** ($r_i=(i+1)L$, $s_i=\max(r_i,e_{i-1})$, busy_ratio, launch_bound_count); it accounts for the GPU idling because the CPU cannot launch fast enough, with **no concurrent slots, no version grid, no staleness**. This problem's idle (stall) is the **trainer starving because generation cannot keep up** — a completely different quantity.
- **vs the `to-*` family of PPO/GRPO objectives** (`to-ppo-clipped-surrogate`, `to-grpo-advantage`, `to-kl-controller`): those are loss/advantage/coefficients formulas that run **after samples are collected**, where $\mu$ enters as the **input** to off-policy correction. This problem sits on the **data-supply side**: it only gets $\mu$, batching and truncation right and **computes no loss value at all**.
- **vs the sibling `rl-colocate-memory-timeline`**: that one accounts multi-model (actor/critic/ref/reward) colocate **memory peaks / offload transfers / phase idle timeline**; this one accounts rollout time and staleness on a **single generation pool** — one is a memory ledger, the other a generation-scheduling ledger. **vs `rl-rollout-shard-repack`**: that one takes already-generated sequences and **re-shards them across DP ranks plus padding-free packing**, accounting token load and transfer counts; this problem never touches "which rank owns which sequence" and only asks "when is it delivered, and how stale is it at delivery".
