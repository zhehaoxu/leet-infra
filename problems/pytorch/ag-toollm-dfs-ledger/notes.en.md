## Sources

- Paper arXiv **2307.16789** (ICLR'24 spotlight), App A.4, verbatim: "Classical DFS algorithms generate multiple child nodes at each step, then sort all the child nodes, and select the highest-scoring node for expansion... we find empirically that in most cases, the nodes ranked highest are often the node generated at first. Therefore, we skip the sorting process of child nodes and choose a pre-order traversal" — exactly the split between `with_filter=False` (DFSDT) and `with_filter=True` (normal DFS) in code.
- **The old todos candidate "pass rate backpropagation" was a misremembering and is corrected here**: the paper's pass rate is a ToolEval metric (PASS rate / win rate) with no relation to the internal tree search. The only backprop-like thing in code is `compute_weight()`, which in master **always returns 0.0** (a ToT Elo leftover; Elo updates live only in `Algorithms/ToT.py`, which is not part of this task). What actually propagates is the **backtrack countdown return value** (2/2/1 and result-1).
- Code location: the original X-PLUG/ToolLLM repo is gone (API returns no `full_name`); it is now **OpenBMB/ToolBench** master. DFS landed in `toolbench/inference/Algorithms/DFS.py` with the 2023-07-27 "update new version" commit; `Tree/Tree.py` provides `make_finish` / `compute_weight` / `get_depth`; `LLM_rank/rank_candidate.py` provides `rank2_subfix` / `rank2symmetry` / `sum_based_rankn`.
- **How the source was fetched**: WebFetch flattens indentation (which is semantic in several places here) and curl against raw.githubusercontent kept getting SIGKILLed, so the GitHub blob API (`/git/blobs/<sha>` + base64) was used to get original bytes. That is what pinned `delete_former_diversity_message = True` **inside** `if len(js_list) > 0:` — assuming it sat at the children level would have produced the wrong rule "mark the previous message invalid even when the diversity list is empty".

## Official quirks (verified one by one)

1. **Entry-test order is the priority order**: `depth >= max_step or pruned or is_terminal` is one condition; inside, `is_terminal` is checked first (terminal → status=1, append to terminal list, return 2), otherwise `pruned = True` and then `observation_code == 4` (give-up → return 2) or return 1. So **terminal beats the depth cap** (a status-3 node at the cap is still recorded as terminal; see `check_depth_cap`).
2. **Backtracking is a countdown**: terminal `final_answer_back_length = 2`, give-up `prune_back_length = 2`, plain pruning 1; a parent with `result > 1` does `return result - 1`. A "2" therefore means "climb back one more level".
3. **The `answer` early exit returns 10000** (not a countdown) and **abandons the remaining candidates at that level**: in the expansion loop `if len(terminal_node) >= answer: return 10000` sits before `elif result > 1`, so once the first subtree yields a terminal, its siblings are dropped without even a `make_finish` — accumulating `answer=2` therefore requires different levels (`check_two_terminals_and_finish_span` builds `[9, 15]` from a two-level tree). The paper says "stop when n answers are found"; the code stops even earlier.
4. **normal-DFS ranking**: every pair is asked **in both directions** (`rank2symmetry` → `score[1 - bigger1] += 1`, `score[bigger2] += 1`), higher total gets +1 and a tie splits +0.5 each (`sum_based_rankn`); `zip_value.sort(key=prior_score, reverse=True)` is a **stable** descending sort (ties keep generation order). Comparison queries (2 per pair) count toward `query_count` and can push the run over budget.
5. **Votes only look at the last character**: `rank2_subfix` tests `output["content"].strip().lower()[-1] == "a"` — `"A is better"` ends with `r`, so it is read as "candidate 1 lost". The official `[-1]` on an empty string raises IndexError; here it is a ValueError.
6. **Three `make_finish` quirks**: the decrement happens **after** marking itself (an Action Input node decrements immediately); recursion continues only while `inter_val >= 0` (stops at `-1`); **the root is an Action Input too**, so on a shallow chain `make_finish(2)` reaches the root while on a three-step chain it stops at the second Action Input (`[3..9]`; 0/1/2 are not marked).
7. **diversity candidates**: for each child, walk the `children[0]` chain down to the first `Action Input` (`while not is_terminal and node_type != "Action Input" and children`); `name` is the Action's `description`, `arguments` the Action Input's `description`, `function_output` the `observation`, `value` is `compute_weight()` **always 0.0**; when `js_list` is empty the whole diversity message is skipped (`delete_former_diversity_message` stays False too).
8. **Budget is checked before node creation**: `query_count += 1` immediately followed by `if query_count >= max_query_count: return 100000` — the over-budget response builds **no Thought node at all** (`check_query_budget` asserts only 4 node types exist).
9. **status three ways**: `4` → `pruned = True` (give-up on entry); `3` → `is_terminal = True` **and** `make_finish(2)`; `1` (hallucinated API name) **does not touch the tree**, it only rewrites `new_message["function_call"]["name"]` to `invalid_hallucination_function_name` (message layer only, not in this ledger — recorded here).
10. **A response without function_call arriving at an Action Input node crashes**: the official code appends `new_message` and then reads `new_message["function_call"]["name"]` → KeyError; here it is a ValueError.
11. **A null response (both content and function_call None) on a Thought node self-recurses**: `temp_now_node` is unchanged, so `self.DFS(temp_now_node, ...)` is `DFS(now_node)` again — `expand_num` gets reassigned and the budget burns down to `max_query_count` (`check_query_budget` sees `expand_order == [0, 1, 1]`, `return_value == 99998`).
12. **Give-up selection is random**: `random.randint(0, len(give_up_node) - 1)` uses the global `random`; here it is exposed as `give_up_seed` (`random.Random(seed).randint`), same semantics and reproducible.

## Authoring notes

- Two expectations were wrong at first, both from guessing: (a) with `answer=1` the first subtree's terminal returns 10000 right away so siblings are never expanded (`expand_order` is `[0, 6]`, not `[0, 6, 3]`); (b) **depth is only checked when a node is entered recursively** — chain construction ignores depth (`max_step=2` still builds the depth-2 Action; the pruned node is the depth-3 Action Input). Lesson: run a trace and print the ledger before locking every assertion.
- **Six mutations SURVIVED the first round**, all fixed by adding scenarios: dual terminal (terminal registration order), three-step deep chain (`make_finish` span), three-candidate 0.5 tie, last-character votes, and default arguments. The 0.5 tie was initially **unobservable** (it only shifts relative order, and both tied sides gain the same amount), so a new ledger field `prior_scores` now exports the ranking score — that is what makes `rank2_subfix` / `sum_based_rankn` scoring actually checkable.
- Three equivalent mutations (proved, no check point): `eq-min-commute` (`(lambda v: (v[0], v[1]))(...)` passthrough is a pure no-op); `eq-expand-num-as-len` (`append` has not happened yet at the assignment site, so `len(expand_order) == now_expand_num`); `eq-sort-desc-vs-neg` (`sorted(key=-s)` and `sorted(key=s, reverse=True)` yield the same permutation without NaN — `reverse=True` stays stable).
- 37 substantive mutations all CAUGHT in the end: backtrack lengths / budget / early-exit constants, four entry-test branches, three `make_finish` points, four ranking points (including unstable tie-break), two countdown returns, four diversity points, two expand-accounting points, budget/tool-key, and two default-argument points.
- Red lines: no real API executor, no LLM judging or token counting (rank tokens are 0), no real `io_state` (`check_success` is folded into status 3), and no message layer (diversity message text, `sift_first_invalid_message`, hallucination rename).
