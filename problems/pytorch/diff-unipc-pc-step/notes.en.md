# Notes: The UniPC B(h) predictor-corrector step reads two different histories

## Core Points and Pitfalls

- **The two sides' "previous output" is not the same tensor.** At line 1194 upstream reads the buffer *before* rotation; only 1201-1205 pushes the current output into `model_outputs[-1]`. So one and the same `mi = model_output_list[-(i+1)]` means something different on each side: on the corrector `m0` is the output at `step_index-1` and the `i=1` difference lands on `step_index-2`, while on the predictor `m0` is already the current output and `i=1` lands on `step_index-1`. One index expression, two different history slots - that is the "not the same source". The statement flattens it: corrector `m0 = m_hist[-1]`, `m_i = m_hist[-(i+1)]`, `s_i = step-(i+1)`; predictor `m0 = m_t`, `m_i = m_hist[-i]`, `s_i = step-i`. Reversing the pairing certainly moves the result for `order>=3`; at `order==2` each side takes a single difference but from a *different* slot (corrector `m_hist[-2]`, predictor `m_hist[-1]`), so writing one shared expression is still caught. Note also that the example's sigma grid is geometric with \(\lambda_i=(i-3)\ln 2\) equally spaced, so \(rk_i=-i\) has the same value on both sides - only the history slots discriminate. `m_hist[-3]` never enters the formula at `(2,2)`, so padding or replacing it must leave the output bitwise unchanged, which is exactly what `check_history_pairing_and_padding` pins.
- **The two 0.5 pins sit at different orders, and they are not symmetric.** The predictor skips the solve at `order_p == 2` (937-938), the corrector skips it at `order_c == 1` (1075-1076), both with the constant 0.5. So "order equals solver_order" does not mean "takes the general path". Measured with the statement's example at `step_index=3`: for `(2,2)` the `bh1`/`bh2` `corrected` values are bitwise identical while `prev` differs by 0.095016; for `(1,1)` and `(1,3)` `corrected` already differs by 0.075117 and `prev` by 0.047508.
- **`B_h` is nearly decorative in this coefficient scheme.** Since `b_i = v_i*f_i/B_h`, solving `Rhos = b` makes the product \(B_h\cdot\text{rhos}\) independent of `solver_type`, so every configuration that takes the general path is bitwise identical under `bh1` and `bh2` - measured `torch.equal` on both outputs for `(2,3) (3,3) (2,1) (3,1)`. Only the two pinned branches let \(B_h\cdot 0.5\) actually land. Those two invariants are the cheapest canary for checking your own transcription.
- **The row/column drop happens on the predictor side only.** Upstream's predictor is `solve(R[:-1, :-1], b[:-1])` (940): the matrix loses a row **and** a column, because the last column belongs to `rk_r = 1`, whose coefficient never enters the solve. The corrector is `solve(R, b)` (1078), and its last coefficient is applied separately to `(model_t - m0)` (1086-1087). Dropping both on the corrector (or neither on the predictor) yields a wrong 3x3 system - or hands the solver a column of ones that makes the matrix badly conditioned.
- **The update order of `factorial` and `h_phi_k`.** Lines 928-929 first do `factorial_i *= i+1` and then `h_phi_k = h_phi_k/hh - 1/factorial_i`. At `hh = -0.693147` (the example) the correct \(v_2\) is -0.097989; using `1/f_i` gives -0.597989, pushing \(b_2\) from 0.391958 to 2.391958, and the `order_p=3` solution under \(B_h=-0.5\) from `[1.506568, -0.949263]` to `[3.506568, -2.949263]` - exactly ±2 apart, because \(\Delta b=[0,2]\) and \(rk_1-rk_2=1\).
- **The terminal sigma=0 is out of scope.** With `final_sigmas_type="zero"` the last step has λ = +inf (α=1, σ̃=0), so \(h=+\infty\), \(hh=-\infty\), \(\varphi_1=-1\). `bh2` gets \(B_h=-1\) and, at order 1, no difference terms at all, so the step lands exactly on \(x_0\); `bh1` gets \(B_h=-\infty\), which is `0 * inf` = NaN at order 1 and ±inf for higher orders once finite differences are multiplied in. The statement therefore demands strictly positive σ and raises `ValueError` instead of asking anyone to reproduce that degenerate cell.
- **`einsum("k,bkc...->bc...")` needs at least three dimensions.** The `torch.stack(D1s, dim=1)` on 935/1070 only reaches 2-D for 1-D samples, and upstream raises `RuntimeError` there. The statement puts "at least two dimensions, dimension 0 is the batch" in the constraints so this trap is not part of the grade.
- **`this_order` lags by one step.** The corrector consumes the `self.this_order` computed during the *previous* step (read on 1194-1199, written on 1207-1213), together with the `lower_order_final` / `lower_order_nums` warm-up. That bookkeeping already belongs to `diff-dpm-solver-order-schedule`, so both orders are explicit arguments here rather than a second thing to get right in the same problem.

## Deviations from Upstream

- The buffer, `timestep_list`, `set_timesteps` and the `step_index` property are flattened into six explicit arguments (`m_hist / m_t / x_last / x_this / sigmas / step_index`); the history pairing is fixed by the statement instead of falling out of "who runs first".
- `convert_model_output` (the ε / \(x_0\) / v conversions and dynamic thresholding) and `solver_p` (the UniP+UniC variant that delegates the predictor to another scheduler, early return on 866-883) are out of scope; the inputs are already in the converted convention.
- Construction-time switches such as `lower_order_final`, `disable_corrector` and `thresholding` are dropped; `predict_x0` / `use_flow_sigmas` / `order_c` / `order_p` become per-call arguments.
- All intermediate math runs in float64 and the two outputs are cast to float32; upstream uses whatever dtype it is handed. The `midpoint/heun/logrho -> bh2` remap (272-276) is kept, but it happens per call rather than at construction.
- The corrector is disabled with `x_last is None` (upstream's `use_corrector=False`); `corrected` then passes `x_this` through unchanged, whereas upstream simply never materialises that intermediate.

## Division of Labor

- `diff-dpm-solver-order-schedule`: the per-step `this_order` / `lower_order_final` / warm-up bookkeeping. Here both orders are arguments.
- `diff-dpm-x0-conversion-threshold`: `convert_model_output`'s convention switching and dynamic thresholding. This problem receives already-converted outputs.
- `diff-dpmpp-2m`: DPM-Solver++(2M) is a predictor-only multistep scheme - no corrector, hence no "two different histories". The increment here is precisely the P-C pair and the index offset it creates.
- `diff-sigma-grid-construct` / `diff-noise-schedule`: building the σ grid and the ᾱ table. Here `sigmas` is an input and only λ is derived from it.
- `diff-ddpm-step` / `diff-ddim-*`: first-order, single-step. With `order_c=order_p=1` the predictor does degenerate to DDIM, and `check_first_order_closed_form` uses that closed form as an independent cross-check.
