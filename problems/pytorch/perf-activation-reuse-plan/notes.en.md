# Deep Dive: Memory Reuse Planning over Lifetime Intervals

## Origin
"Given lifetime intervals, assign each value an address offset" is **storage allocation** in compiler terms, and it is the same idea as **interval-graph coloring** in register allocation: values alive at the same time must occupy different addresses, i.e. the "lifetime graph" — an interval graph — must be coloured. Interval graphs are perfect, so with **equal sizes** the minimum number of colours is exactly the maximum clique size (the number alive at some instant), and greedy colouring by left endpoint is optimal. With unequal sizes the problem becomes the weighted version, which is NP-hard, and real implementations fall back to heuristics: TensorFlow's grappler memory optimizer and TorchScript's static memory pool both place large tensors first at the lowest feasible offset. This problem exercises that heuristic together with the **attainability lower bound**. Contrast with `perf-allocator-block-fit`: that one is an online allocator (alloc/free timing, free-block coalescing); this one is **offline static planning** (all lifetimes known up front, no time ordering).

## Key points and pitfalls
1. **Only lifetime overlap constrains you**: two tensors with disjoint lifetimes may be fully stacked at the same address — the essential difference from ordinary bin packing. Test overlap with half-open intervals: `max(s1,s2) < min(e1,e2)`; equality counts as disjoint.
2. **Placement order is fixed as size-descending** (ties by start/end/index): big blocks go first so small ones do not shatter the address space. Any other order changes the peak, and the judge cross-checks this exact order.
3. **The smallest feasible offset only needs a few candidates**: 0, plus the end offset of every already placed, lifetime-overlapping tensor. If the smallest feasible `o>0` were not a candidate, then `o-align` would also be feasible (whatever blocks it must end at `o`) — contradiction, so the candidate set is complete.
4. **The bound is only a bound**: `lower_bound` is the maximum simultaneous live-byte sum; greedy-by-size can exceed it when gaps cannot fit later arrivals. The tests include a fragmentation case with `peak=4 > lb=3`; do not treat it as an optimality check.
5. **Aligned sizes drive both ordering and the peak**: round `nbytes` up before sorting and before comparing peaks, otherwise 100 vs 1 at align 64 yields the wrong order.
6. **Return offsets in input order**: processing is size-sorted internally, so the output must be mapped back to original indices or the whole table shifts.

## Verification
The reference keeps a placed list and uses candidates "0 ∪ ends of already placed overlapping blocks", taking the first conflict-free one. The judge `_oracle` never builds candidates; it **jumps right**: starting at 0, whenever it hits a placed block it jumps straight to that block's end (the furthest end among several conflicts), and the first non-conflicting position is the smallest feasible offset. The lower bound uses an event sweep (at equal times, ends settle before starts, matching the half-open convention). The two structures are compared item by item over 40 random lifetime sets. Additional assertions: offsets and sizes are aligned; lifetime-overlapping tensors never share bytes; shifting any tensor left by one slot always collides (minimality); `peak >= lower_bound`; three lifetime-sequential tensors all reuse offset 0; fully overlapping tensors stack by size; the fragmentation case has `peak=4 > lb=3`; alignment rounding and the empty input degenerate correctly.

## Complexity
The reference is `O(N²·C)` (`N` tensors, up to `N` candidates each, each candidate compared against `O(N)` placed blocks); the lower bound is `O(N²)`. The judge oracle's jump search is polynomial as well — the scales are small and only correctness matters.
