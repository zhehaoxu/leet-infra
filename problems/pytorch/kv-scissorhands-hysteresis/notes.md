# 解题说明 · ScissorHands

## 为什么要滞回

单帧打分剪枝把「重要性」当成独立同分布的观测，但解码期的注意力分布**逐帧抖动**：一次格式性 token 的出现就能把注意力质量整块拉走。如果逐帧做 top-k，被误杀的关键 token 无法恢复。ScissorHands 的滞回就是给决策加了一个「连续 \(m\) 帧确认」的缓冲：只要中间有一帧回升，计数器清零，token 继续存活。

代价是**反应延迟**：真正的失效要到第 \(m\) 帧才生效。这就是 `patience` 的权衡——\(m\) 越大越稳但越迟钝，\(m=1\) 就退化成无记忆的阈值剪枝。

## 计数器的三个坑

1. **严格小于**：`score < tau` 才是低分。用 `<` 而不是 `<=`，示例里 `score == 0.5` 与 `τ = 0.5` 的用例会把两者区分开。
2. **回升即清零**：不是「累计低分帧数」，而是「**连续**低分帧数」。中途任何一帧 `>= tau` 都让计数归零，否则长期零星抖动的 token 会被慢慢「攒」死。
3. **先更新再判定**：当步的分数先计入计数，再看是否达标。若先判定后更新，驱逐步号会整体晚一步。

## 驱逐不可逆

实现里可以只在 `evict_step < 0` 时才允许写入驱逐步号（`& alive`）。真实系统里被驱逐的 token 已从缓存移除，其后续「分数」根本不存在；如果允许「救回」，滞回就退化成滑动窗口平均，语义完全不同。

## 与单帧打分题的分工

现有 `kv-snapkv-pooling`、`kv-knorm-importance`、`kv-tova-head-mean` 等题都只算**一次**打分与 top-k，属于「选谁」。本题不引入新的打分器，专攻「**何时**真的删」——时间维度上的决策滤波，与打分器的选择正交。

## 复杂度

\(O(SL)\) 时间、\(O(L)\) 额外空间：每步只做一次逐元素比较、一次计数更新、一次比较判定。无需排序，也不需要保存完整历史分数，流式即可。

## 相关题目

- `kv-snapkv-pooling` / `kv-knorm-importance`：单帧打分与选择（本题的上游）。
- `kv-streaming-llm-sink`：位置规则固定，不涉及时间决策。
- `kv-h2o-heavy-hitters`：用累计分做决策，属于「记忆在分数里」；本题把记忆放在**判定**里，两者可以叠加。
