# 解题说明 · n-gram 池的老化

## 三件事各自容易错在哪

- **预测**：`max(table.values())` 只给计数，不给 token。要同时按「计数降序、token 升序」排序，否则并列时结果依赖字典迭代顺序，判题会随实现变化而抖动。
- **学习**：最容易写成「把预测出的 token 再 +1」。那样一来，模型的错误猜测会自我强化成一个死循环（预测 A → 计数 A 更大 → 更倾向预测 A），命中率看起来漂亮但草稿质量崩塌。正确做法永远用真实 token 更新。
- **淘汰**：只做 LRU 是最常见的简化，但会和「高频优先」冲突：一个出现 50 次的老 n-gram 因为是 3 步之前用的，就被一个只出现 1 次的新 key 挤掉。三元组 `(总计数, 时间戳, key)` 把两种诉求叠加起来：计数决定生存权，时间戳只做同分排序。

## 为什么时间戳要全局单调

如果时间戳用「步内序号」或「该 key 自己的计数」，不同 key 之间的新旧就不可比。用全局单调时钟后，`stamp[k]` 的大小关系严格等价于「谁更久没被用过」，淘汰与老化才有唯一解，也让判题可复现。

## 初始裁剪

`prompt` 可能有几千个 token，切出来远超 `capacity`。如果只在每次查询后裁剪，第一帧的 `size` 会是原始条目数（虚假膨胀），而且第一次淘汰会一次吐出几百个 key，`evicted` 序列完全失真。所以初始建池后必须立刻裁一次。

## 边界

- `capacity = 1`：每学一个新 key 就会把别人踢掉，池永远只有一个 key。若这个 key 是高频的，它会稳定存活——这正是「计数优先」的直接体现。
- `n = 1` 且 `prompt` 很短：key 只有一两个，几乎全部命中；`n` 越大越稀疏，命中率下降但预测更靠上下文。
- `observed` 为空：四个输出都是长度为 0 的张量，池的构建照常完成（但 `size`/`evicted` 没有观测点）。
- 未命中的定义是「key 不在池里」，与「key 在池里但后继不在计数表里」不是一回事——后者不可能发生，因为插入时必然带一个后继。

## 复杂度

每步一次哈希查找 + 一次 \(O(N)\log\) 的裁剪（\(N\) 为池大小）；实现上可以用最小堆把裁剪降到 \(O(\log N)\)，但需要惰性删除。真实系统里池大小是千级，线性扫描完全可以接受。
