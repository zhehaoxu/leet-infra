# 检测：RLE 编解码与 mask IoU

## 题目描述

实例分割的评测（COCO 的 mask AP、Mask R-CNN 的验证）几乎每一步都要算「两个掩码的交并比」。真实数据集里掩码不会以稠密矩阵存储：一张 1024×1024 的图里目标可能只有几百个像素，稠密存法既占内存又难压缩。COCO 的做法是把掩码按**列优先**顺序扫成一串 0/1，再用游程编码（RLE，run-length encoding）压成 `counts`：从背景开始交替记录每段连续同值的长度。

于是 mask IoU 变成了一道**格式题**而不是像素题：给定一块稠密掩码与另一块的 RLE，要算出两者的交集、并集与 IoU，并顺便把稠密掩码重新编码成规范 RLE。两个容易踩的坑：

- **列优先**：`counts` 的线性顺序是「先走完整整一列」，行优先编码在同一块掩码上会给出完全不同的数组；
- **规范形式**：首项是背景游程（可以为 0），其余每项必须为正，末尾的背景游程不能丢。

本题要求把这两件事做对，并且允许在**不把 counts 展开成稠密掩码**的前提下，直接对两份游程做归并来求交。全 CPU、确定性、不调用随机数。

## 规则

完整签名、参数含义与默认值只写在 starter 的 docstring 里，那是唯一判题口径。

- 稠密掩码是 \( (H,W) \) 的 bool 或 uint8 张量，元素只能是 0/1；`size` 是长度 2 的整数序列 \( (H,W) \)，必须与掩码形状**完全一致**，\(H,W\ge1\)。
- `counts` 是一维整型张量，表示另一块掩码的 COCO RLE：
  - 按**列优先**顺序遍历，线性下标 \( \mathrm{lin}=x\cdot H+y \)（\(x\) 为列、\(y\) 为行）；
  - 游程值从 0（背景）开始交替，`counts[0]` 是第一个前景像素之前的背景长度（可为 0），之后奇数下标为前景段、偶数下标为背景段；
  - 元素非空、全部非负、**除首项外不得为 0**（规范形式，不允许内部零长游程），且元素之和等于 \(H\cdot W\)。
- 返回四元组：
  - `iou`：0 维 float64，\( \mathrm{inter}/\mathrm{union} \)，`union` 为 0 时取 0；
  - `intersection`：0 维 int64，两块掩码同时为前景的像素数；
  - `union`：0 维 int64，至少一块为前景的像素数 \( =|A|+|B|-|A\cap B| \)；
  - `counts_a`：一维 int64，稠密掩码的**规范**列优先 RLE。
- 规范编码的细节：全背景编码为 `[H*W]`；列优先扫描的第一个像素就是前景时首项写 0（例如 `[0, H*W]` 表示全前景）；末尾若是背景，背景游程必须包含在内；相邻同值段必须合并，因此不会出现内部 0。
- 非法输入一律抛 `ValueError`：掩码不是张量/不是二维/dtype 不是 bool 或 uint8/含 0、1 以外的值；`counts` 不是一维整型张量/为空/含负值/除首项外出现 0/元素和不等于 \(H\cdot W\)；`size` 不是长度 2 的整数序列/非正/与掩码形状不一致。
- 不修改任何输入张量。

## 示例

\(H=2,W=3\)，列优先的线性下标与坐标对应关系是

```
lin   :  0    1    2    3    4    5
(x,y) : (0,0)(0,1)(1,0)(1,1)(2,0)(2,1)
```

掩码 A（稠密）与掩码 B（以 RLE 给出）：

```
A 行优先矩阵 = [[1, 0, 0],
                [0, 0, 1]]
B 行优先矩阵 = [[1, 1, 0],
                [0, 1, 1]]
```

按列优先展开：

```
A :  1  0  0  0  0  1   ->  counts_a = [0, 1, 4, 1]
B :  1  0  1  1  0  1   ->  counts   = [0, 1, 1, 2, 1, 1]
```

`counts_a` 的读法：首项 0 表示「第一个像素就是前景」，接着 1 个前景像素、4 个背景像素、1 个前景像素，合计 6。`counts` 的读法：0 个背景、1 个前景、1 个背景、2 个前景、1 个背景、1 个前景，合计 6。

交集出现在 `lin=0` 与 `lin=5`，于是

```
intersection = 2
|A| = 2, |B| = 4  ->  union = 2 + 4 - 2 = 4
iou = 2 / 4 = 0.5
```

本例 A 的行优先展平恰好与列优先相同（都是 `[1,0,0,0,0,1]`），所以这一例区分不出两种顺序。判别用例如下：掩码 `[[1,1,0],[0,0,0]]` 的列优先展平是 `[1,0,1,0,0,0]`，编码为 `[0,1,1,1,3]`；行优先展平是 `[1,1,0,0,0,0]`，编码为 `[0,2,4]`。把 `[0,2,4]` 当作列优先 RLE 解码，与 A 只剩 1 个交集像素，IoU 为 \(1/3\) 而不是 1。

## 约束

- 返回顺序固定为 `(iou, intersection, union, counts_a)`；`iou` 为 0 维 float64，`intersection`/`union` 为 0 维 int64，`counts_a` 为一维 int64。
- 判题对 `iou` 用绝对容差 \( 10^{-12} \)（数值只有整数比，float64 下精确），对 `intersection`、`union`、`counts_a` 用 `torch.equal` 逐元素比对。
- 两张空掩码的 `union=0` 时 `iou` 约定为 0，不产生 NaN。
- CPU、确定性、不调用随机数；`counts` 用 int32 还是 int64、掩码用 bool 还是 uint8 都不影响结果。
