# 详解：检测：RLE 编解码与 mask IoU

## 出处

- COCO 数据集与掩码格式：Lin et al., *Microsoft COCO: Common Objects in Context*, ECCV 2014, arXiv:1405.0312。COCO 的 `segmentation` 字段对每个实例存一份 `{"counts": [...], "size": [h, w]}`，即本题的 RLE 形式。
- 官方实现：`cocodataset/cocoapi` 的 `common/maskApi.c`。`rleEncode` / `rleDecode` 负责稠密掩码与游程的互转，`rleIou` 直接在两份 `counts` 上做归并求交——本题目的是重建这三件事；`maskUtils.iou(dt, gt, iscrowd)` 则是它在上层的用法（掩码 IoU 矩阵）。
- **列优先**的约定在官方接口里写作「Fortran order」：`maskUtils.encode(np.asfortranarray(mask))`，与 MATLAB 的列主序是同一传统。
- 判题环境没有 pycocotools，参考解用 `torch.unique_consecutive` 做编码、用双指针做归并；CPU、确定性、无随机数。

## 完整推导与下标约定

**线性化**：对 \( (H,W) \) 的掩码定义

\[
\mathrm{lin}(x,y)=x\cdot H+y,\qquad x\in[0,W),\ y\in[0,H),
\]

也就是先走完 \(x=0\) 这一列的 \(H\) 个像素，再进入 \(x=1\)。按 \( \mathrm{lin} \) 升序读出的 0/1 序列就是 RLE 的底层序列。torch 里等价于 `mask.permute(1, 0).reshape(-1)`（`permute` 后是非连续视图，`reshape` 会按新顺序复制）。**行优先**则是 \( \mathrm{lin}=y\cdot W+x \)，在同一块掩码上与列优先给出不同的数组。

**规范编码**：设底层序列为 \( s_0,\dots,s_{HW-1} \)。先把它压成极大同值段 \( (v_0,n_0),\dots,(v_{R-1},n_{R-1}) \)，其中相邻段的值必然不同。约定游程从背景开始交替，因此

\[
\text{counts}=
\begin{cases}
[0,\ n_0,\ n_1,\ \dots] & v_0=1\ (\text{序列以} 0 \text{ 开头时首项补 } 0),\\
[n_0,\ n_1,\ \dots] & v_0=0 .
\end{cases}
\]

这直接给出三条可判定的性质：首项可为 0、其余项必为正、元素和恒为 \(HW\)。注意「末尾背景游程」自动包含在内，因为极大同值段覆盖整个序列；反过来，如果实现只记录前景段、把背景段当分隔符丢掉，末尾的背景长度就丢了，`sum(counts)` 会小于 \(HW\)，与「元素和必须等于 \(HW\)」的校验互相矛盾。

**用归并求交**：两份 counts 各自是同一段线性区间的划分，只是切点不同。双指针同时走：

\[
\text{每次取 } t=\min(\text{rem}_a,\text{rem}_b),\quad
\text{若两侧当前游程值都为 1 则 } \mathrm{inter}\mathrel{+}=t .
\]

推进到某侧剩余长度为 0 时前进一格并把该侧游程值翻到另一侧（等价于下标奇偶：偶数下标背景、奇数下标前景）。全程 \( O(R_a+R_b) \)，不需要把 counts 展开成 \(HW\) 个元素。参考解的实现里 `va = ia & 1` 就是在用奇偶取游程值，避免维护额外的翻转变量。

**面积与并集**：\( |A| \) 可以直接对掩码求和（掩码本来就是稠密输入），\( |B| \) 是 counts 的**奇数下标**之和——偶数下标是背景。用

\[
\mathrm{union}=|A|+|B|-\mathrm{inter}
\]

而不是再走一遍归并求并，少一份状态、也不会与交集算错方向。两块全背景时 \( |A|=|B|=\mathrm{inter}=0 \)，`union=0`，此时 IoU 约定为 0：\( 0/0 \) 不能进浮点。

**IoU 用 float64**：交集与并集都是整数，比值在 float64 下对本题规模精确；即便写成 `inter / union` 的 Python 除法再建 0 维张量，也要显式 `dtype=torch.float64`，否则默认 dtype 会跟随全局设置。

**校验口径**：`counts` 的每条规则都对应一种真实错误——负值（损坏的编码）、内部 0（未合并的相邻同值段）、和不为 \(HW\)（尺寸记错或丢了末尾背景）、空张量（\(HW\ge1\) 时不可能）。`size` 必须与 `mask.shape` 完全一致，是因为 COCO 的 `rle["size"]` 与 counts 是分开存的，错配时官方代码会静默算出错误结果，本题选择显式报错。`mask` 允许 bool 与 uint8，但 uint8 里出现 2 就要报错，否则「0/1 掩码」的语义被破坏。`counts` 允许 int32 与 int64，但求和前要转 int64：大掩码的 `int32.sum()` 会溢出。

## 核心与易错点

1. **列优先，不是行优先**：判别用例是掩码 `[[1,1,0],[0,0,0]]`——列优先编码 `[0,1,1,1,3]`、行优先编码 `[0,2,4]`；把 `[0,2,4]` 当列优先喂回去，IoU 从 1 掉到 \(1/3\)。
2. **首项可为 0 且必须保留**：列优先第一个像素就是前景时，`counts` 以 0 开头；写成 `[n_0, ...]` 会整体错位一格，后续每一段都读反。
3. **末尾背景游程不能丢**：只记前景段的实现会少掉尾部背景，`sum(counts) < HW`；`[0,2,2]` 与 `[0,2]` 的区别就是第二列那 2 个背景像素。
4. **相邻同值段必须合并**：`[0,1,0,3]` 这类内部 0 是非规范编码，要报 `ValueError` 而不是「碰巧能解码」。
5. **交集按并集定义反推**：`union = |A| + |B| - inter`；不要用 `|A| + |B| + inter` 或再归并一遍求 OR 后忘记减交集。
6. **`|B|` 只加奇数下标**：偶数下标是背景游程，加进去会把背景当面积。
7. **两张空掩码的 IoU 是 0**：`union=0` 必须短路，否则 `0/0` 得到 NaN，判题的 `abs(iou-0)<tol` 直接失败。
8. **`counts` 求和转 int64**：int32 输入在大 size 下 `sum()` 溢出成负数，会把合法输入误判成「和不对」。
9. **uint8 只接受 0/1**：uint8 常被当作「非零即前景」，但本题约定元素只能是 0/1，2、255 都是非法输入。
10. **`size` 不等于掩码形状要报错**：这是 COCO 里真实存在的错配（`size` 与 `counts` 分开存），不要静默用掩码形状覆盖。
11. **不改输入**：`permute` 后 `reshape` 会复制，不会原地改掩码；返回的 `counts_a` 是新张量。
12. **返回标量形状**：`iou`/`intersection`/`union` 都是 0 维张量（`torch.tensor(v)`），不是 Python 标量也不是长度 1 的向量。

## 与邻近题的区别

- **vs `vision-map-coco`（同批次）**：mAP 里匹配用的是**框**的 IoU（面积按矩形算），没有掩码、没有 RLE；本题是**像素级**掩码 IoU，难点在列优先的游程格式与归并。
- **vs `vision-anchor-match` / `vision-fcos-centerness`（同批次）**：那两题的 IoU 都作用在 anchor/预测框与 GT 框之间，用于训练目标分配；本题不涉及任何检测框。
- **vs `vision-rotated-nms`（同批次）**：旋转框 IoU 是**多边形**求交（Sutherland–Hodgman 裁剪），输入是连续的顶点坐标；本题是**离散像素**集合求交，输入是压缩过的整数游程，交集天然是整数。
- **vs `where-select` / `masked-*` 之类算子题**：那些题在稠密张量上做逐元素选择，内存 \(O(HW)\)；本题的考点恰恰是**不展开** counts，只读掩码一遍 + 归并两份游程。
- **vs `searchsorted-bincount`**：那是值→桶的直方图原语；本题的游程归并与直方图无关。

## 对拍口径与复杂度

- **主 oracle**：`_oracle` 把 counts 稠密展开成 `HW` 个 0/1（`flat_b.extend([cur]*n)`），再与掩码的列优先展平逐位 `zip` 统计交/并，最后用一个独立的线性 `_rle` 扫描重算编码；参考解用 `unique_consecutive` 编码、双指针归并求交，结构完全不同。尺寸覆盖 1×1、1×7、7×1、5×4、6×6，包含全背景、全前景、棋盘格与算术图案。
- **判别性用例**：示例的 `counts_a=[0,1,4,1]`、`counts=[0,1,1,2,1,1]`、交 2 / 并 4 / IoU 0.5；列优先 vs 行优先的 `[0,1,1,1,3]` 与 `[0,2,4]`（错序时 IoU=1/3）；6 组规范编码（全背景 `[HW]`、全前景 `[0,HW]`、首项 0、末尾背景、多段交替、无首项 0）；自比较恒等；子集/互斥/空-满/双空；bool 与 uint8、int32 与 int64 同结果、输入不被修改；18 组非法输入。
- **实测非显然事实**：示例里 A 的行优先与列优先展平**恰好相同**，所以示例本身区分不出顺序——真正的判别在 `check_column_major`；把 `[0,2,4]` 当列优先解码后交集只剩 1 个像素，IoU 恰好 \(1/3\)，这个数值是错序实现的指纹。
- **复杂度**：编码必须读一遍掩码，\( O(HW) \) 时间与一份展平副本的内存；归并 \( O(R_a+R_b) \)。判题规模最大 6×6，远低于时限。真实系统（COCO `rleIou`）也是这个结构：面积用 `rleArea`、交集用归并，从不物化 \(HW\) 的稠密掩码。
