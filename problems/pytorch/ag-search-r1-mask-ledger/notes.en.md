# notes (ag-search-r1-mask-ledger)

## Sources

- Paper arXiv **2503.09516** (Search-R1, 2025) §3: in a multi-turn rollout the model alternates `<search>query</search>` and `<answer>ans</answer>`, and retrieved documents are spliced back as `<information>…</information>`. Training uses an outcome reward, so the observation span **must be excluded from the loss** (`info_mask`); otherwise the model learns to imitate the retriever's documents.
- Code: `PeterGriffinJin/Search-R1` main — `search_r1/llm_agent/generation.py` (blob `6b68cb003ac3f943d45eb8d5cf48a7ebee5cd1f6`, 470 lines); `tensor_helper.py` (`15a7c7c084c4f952533f43b214f987db81075255`, 75 lines: `cut_to_effective_len` / `convert_pad_structure` / `create_attention_mask` / `create_position_ids` / `_example_level_pad`). Fetched via the GitHub blob API with base64 for the original bytes (`raw.githubusercontent` occasionally gets SIGKILLed, and WebFetch eats indentation).
- Upstream is verl: `run_llm_loop` rewrites the rollout in `verl/trainer/ppo/ray_trainer.py`, and `DataProto` batches are rank-2 tensors (left-padded prompts, right-padded responses). This task strips the tensor layer and keeps a **per-row token ledger**.

## Official quirks (verified one by one)

1. **Truncation priority is position-independent**: `_postprocess_responses` tests `'</search>' in resp` first, then `'</answer>'`, and both branches are `split(...)[0] + close_tag`. So an "answer then search" generation keeps the whole search span (while the action is `answer`), and an "search then answer" one loses the answer entirely. `check_search_priority_cut` pins both directions.
2. **Parsing follows `re.search` semantics, not "the first close tag"**: `<(search|answer)>(.*?)</\1>` with DOTALL. When an opener has no close tag of its own the regex backtracks to the next opener, so a bare `</search>` gives action `None` (a retry), not search. Same-kind nesting takes the **nearest** closer.
3. **Re-tokenizing eats special tokens**: `batch_decode(skip_special_tokens=True)` → string → `_batch_tokenize`. `<|im_end|>` is neither in the policy span nor in the token count. This differs from "keep the ids and mask them out"; this task follows the official behaviour.
4. **The retry prompt is joined by single spaces**: the source reads
   ```python
   next_obs.append(f'\nMy previous action is invalid. \
   If I want to search, ...')
   ```
   the backslash continuations **inject no newline** and the continuation lines start at column 0, so the text is `"...invalid. If I want to search, ..."`. This task passes it in as `wraps["retry"]` and only checks how many tokens it costs and that it is masked 0.
5. **Observations are truncated from the front**: `_process_next_obs` does `next_obs_ids[:, :max_obs_length]`. With the real config (`max_obs_length=500`, three documents per observation) an over-long observation loses its tail, `</information>` included — a format corruption that really happens in training. The retry prompt goes through the same function.
6. **Training side is prefix-anchored, context side is suffix-anchored**: `_update_right_side` uses `[:, :max_len]`, `_update_rolling_state` uses `[:, -max_len:]`. The two windows of one rollout can therefore differ completely: after the cap the answer reaches the context but not the loss. `check_two_windows` pins them to two different 6-tuples with `max_prompt_length=6`.
7. **The `min` collapse**: `max_len = min(P, eff)` with `eff = max_j own_j`, and each row keeps `min(own, max_len)`. Since `own <= eff`, `min(own, min(P, eff)) = min(own, P, eff) = min(own, P)` — **the batch maximum never affects any row**, so a per-row computation is exact (a fidelity proof, not an equivalence mutation).
8. **The two faces of `0`**: `max_prompt_length=0` makes the right side `[:0]` empty and the context `[-0:]` complete; `max_start_length=0` makes `prompt[-0:]` equal `prompt[0:]` (the whole prompt). Both are pinned in `check_zero_prompt_length` / `check_prompt_tail`.
9. **Three semantics of the final rollout**: with `do_search=False`, `search_results` degrades to `[''] * n`, the observation `'\n\n<information></information>\n\n'` is **discarded** (bound to `_`), `turns_stats` is not updated, and `dones=0`. So a row that searches again on the last turn **never counts as finished**, and `turns` can equal `max_turns + 1`.
10. **`turns_stats` always equals the number of generations**: it starts from `torch.ones` and is incremented only for rows that are still active after each step; k main-loop steps plus one final rollout is k+1 generations, and a row that finishes on step k' gets exactly k'. `check_active_num_list` pins `[3, 2, 2, 2]` with a mixed batch (answered / always-searching / always-invalid).
11. **`if next_obs_ids != None:` is a tensor comparison**: measured on torch 2.x, `tensor != None` hits `__ne__`, returns `NotImplemented`, and Python falls back to identity comparison → `True`. So the line behaves as `is not None`; answer rows pass a **pad-only row** (empty string padded to `'longest'`), which contributes zero real tokens to the ledger.
12. **Pad tails exist but are not booked**: a finished row still gets a pad block appended every step, and after `[:, :max_len]` it may keep `cap - content_len` trailing pads. They are always 0 in `attention_mask` / `info_mask`, and `(cumsum-1)*attn` drives their position id back to 0 — so this task books only real tokens and states that exclusion explicitly in the description.

## Engineering notes

- My first `check_default_args` passed while the oracle itself was wrong: `left = prompt[len(prompt) - S:]` yields a **negative-index window** when `S > len(prompt)` (a 300-token prompt with `S=512` keeps only the last 212), whereas the official `prompt[-512:]` keeps everything. Fixed to "whole prompt when `S == 0 or S >= len`". That bug turned into a checkpoint: `check_prompt_tail` pins `S=0`, `S=1` and `S=512`.
- Adjacent same-kind segments must be merged: the final rollout's policy follows the last main-loop policy with no observation in between, and without merging you get `[["policy",4],["policy",1],["policy",2]]`. The oracle flattens to `(kind, id)` pairs and compresses runs, while the solution merges while accumulating; two independent paths agreeing is what makes the segmentation convention well defined.
- `check_errors` **must call solve directly**: the first version went through `_led`, which also runs the oracle, so the reference solution's own `ValueError("negative bound")` covered for the mutant that removed the bound check, and `m-bound-no-check` SURVIVED. Calling solve directly caught it immediately. This is the generic trap for domain-constraint problems.
- Two case-level details: the second scenario of `decode_drop` needs a second generation (after dropping `<|im_end|>` the `<search>` is still the action, so the row does not end); the "missing generation" case in `errors` needs a row that keeps going (always searching), otherwise it answers and breaks before consuming turn two.
- The defaults check builds three long inputs on purpose: a 23-token observation (catches `max_obs_length=16`), a 42-token generation (catches `max_prompt_length=32`), a 300-token prompt (catches `max_start_length=256`), plus `turns=4` (catches `max_turns=4`). Each default is caught by its own assertion.
- All 47 mutations are CAUGHT with 0 equivalences: truncation 4, parsing 3, special tokens 2, observations 4 (including an off-by-one), turns/stats 6, windows 5, masks 3, segments 2, domain constraints 3, defaults 5, misc 10. Nothing unobservable survives, because the task is a ledger that exposes every intermediate quantity (`segments` / `dropped` / `obs_truncated` / `rolling_ids`).
- 60 randomized comparisons: random shapes (`max_turns 0..3`, `S ∈ {0,1,2,512}`, `P ∈ {0,3,8,64}`, `O ∈ {0,1,4,32}`) with random generations (unclosed tags, special tokens, zero-length generations); `search_results` is a dict subclass whose `__contains__` is always true so random queries resolve (and `deepcopy` preserves that).
