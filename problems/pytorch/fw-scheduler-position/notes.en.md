# Explained: Where lr_scheduler.step() Sits in the Training Loop

## Origin

PyTorch optimization docs *How to adjust Learning Rate* and `torch.optim.lr_scheduler`: since 1.1.0 the official convention is `optimizer.step()` **before** `lr_scheduler.step()`; calling the scheduler first triggers the UserWarning "Failure to do this will result in PyTorch skipping the first value of the learning rate schedule". Mechanism: `LRScheduler.__init__` already runs one "preview" `self.step()` (which lands `last_epoch` on 0, the undecayed base lr), so the lr effective at step \(i\) corresponds to the \(i\)-th decayed schedule value; `StepLR.get_lr = base_lr * gamma ** (last_epoch // step_size)`. `ReduceLROnPlateau` is metric-driven rather than epoch-driven: mode/threshold(rel)/patience/cooldown/factor/min_lr all live in the `lr_scheduler.py` state machine; `best` updates only on improvement and `min_lr` is a hard floor.

## Key points and pitfalls

1. **"When you record" is "what the grader sees"**: this problem records lr before `opt.step()` — variant A's entry 0 is \(0.1\) (full base_lr) while variant B's is \(0.05\) (the first schedule slot skipped). Both runs end with `last_epoch=4` — same counter ≠ same trajectory.
2. **The final weight is the observable consequence of the position difference**: \(w_{k+1}=w_k(1-2\,lr_k)\); A takes one more big-lr first step, ending at 0.667 < B's 0.823. The lr ledger alone is not enough — the grader also back-checks via the weight ledger.
3. **Plateau's patience means "drop only after bad steps *exceed* patience"**: patience=1 → two consecutive bad metrics trigger one drop; the counter resets after each drop.
4. **Hitting the min_lr floor does not exempt the drop action**: the second drop \(0.5\to0.25\) is pushed back to 0.3 (and the third, \(0.3\to0.15\), is likewise pinned at 0.3), yet `num_bad` still resets each time — externally it looks like "every patience-saturated bad step 'dropped', just without changing anymore".
5. **The threshold test is the relative form** \(m < best\cdot(1-10^{-4})\): with monotonically worsening metrics, once best is recorded as 1.0 it never updates again.

## Cross-check basis

The solution runs the real schedulers; the `_oracle` is pure Python: StepLR is generated by the closed-form power formula \(0.1\cdot0.5^i\) for both lr sequences (bitwise identical to the framework under IEEE), weights via the \(w(1-2lr)\) product; Plateau is replayed metric by metric through a hand-written improved/num_bad/reduce state machine. Additional assertions: "B[0]==A[1]", "both variants share last_epoch but differ in weight", "the plateau floor-pinned sequence".

## Complexity

An \(O(\text{steps})\) pure bookkeeping exercise — instantaneous.
