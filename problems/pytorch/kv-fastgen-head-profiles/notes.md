# 解题说明 · FastGen

## 为什么按头分类

同一层里不同头的注意力模式差异极大：有的头像「分隔符探测器」，质量死死压在几个标点上；有的头要回溯整段 prompt 做信息聚合；还有的头只看最近几个 token 保证局部流畅。FastGen 的做法是给每类头配一种**天生适合它**的压缩策略，而不是让所有头共用一个 top-k。

这与 `kv-duo-attention-heads` 的二分类（检索头/流式头）同源但更细：DuoAttention 只区分「要不要保 sink+window」，本题多出 specialized 类，还要求**不同类拿不同预算**。

## 两个统计量的直觉

- \(R_h\) 近因占比：把「只看最近 window 的比重」当作流式倾向。它用**最后一个 window 的质量占比**而不是「平均位置」，对右偏分布最敏感。
- \(C_h\) 集中度：单个最大值占比。它捕捉「尖峰」——specialized 头的特征是把质量砸在极少数 token 上。用 max 而不是熵，是为了让阈值可解释、可手算。

两者都不需要排序，一次 reduce 即可，天然适合在 profiler 里流式统计。

## 为什么先判 streaming

`R` 达标说明头的注意力**几乎全部落在近窗**，这时保 sink + window 已能覆盖它的需求，打分策略反而多余。若先判 specialized，一个同时「尖峰且近因」的头会被拉去做 top-k，浪费了位置策略更便宜的优点。判定顺序本身是算法的一部分，题面固定为 streaming 优先。

## 位置策略 vs 打分策略

streaming 分支是本题最容易被写错的地方：它**不看分数**。哪怕末窗内全是 0、中间段有个巨大尖峰，也照样保留末窗、丢弃尖峰。这不是 bug 而是设计——流式头的需求是「位置的连续性」，用分数去挑会破坏局部语法窗口的完整性。

## 并列与边界

top-k 用「降序 + 并列取小下标」，与全库其它题一致；`k` 允许超过候选数，此时取满即可。阈值比较统一用 **`>=`**（取等归入该类型），这让人工核算例可以精确落在边界上。

## 复杂度

\(O(HL)\) 统计 + \(O(HL\log L)\) 排序（每个头一次），空间 \(O(HL)\) 输出掩码。真实实现会按头并行，单头 \(O(L\log L)\)。

## 相关题目

- `kv-duo-attention-heads`：二分类 + 固定 sink/window，不做预算差异化。
- `kv-pyramid-layer-budget`：在**层**维度分配预算；本题在**头**维度分配，两者正交。
- `kv-streaming-llm-sink`：纯位置策略的基线，等于本题的 streaming 分支。
