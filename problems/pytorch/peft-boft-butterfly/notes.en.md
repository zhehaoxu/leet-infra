# Notes · BOFT's Orthogonal Transform via Butterfly Factorization

## Where it comes from

- `huggingface/peft`, `src/peft/tuners/boft/layer.py`: `cayley_batch(data)` first computes `skew_mat = 0.5 * (data - data.transpose(1, 2))`, then `Q = torch.linalg.solve(id_mat + skew_mat, id_mat - skew_mat, left=False)`; `update_layer` precomputes the buffer `boft_P` of shape `(nbf+1, d_in, d_in)` with `block_butterfly_perm(self.in_features, int(boft_block_num / 2**i), int(boft_block_size / 2), boft_n_butterfly_factor)` plus `perm2mat` (`perm_mat[i, idx] = 1`), registers `boft_R` as `(nbf+1, block_num, block_size, block_size)` and `boft_s` as `(out_features, 1)`; in `get_delta_weight` the accumulation is `butterfly_oft_mat = batch[0]` followed by `for i in range(1, N): butterfly_oft_mat = batch[i] @ butterfly_oft_mat`; the unmerged path of `Linear.forward` transposes the weight to `(in, out)`, does `torch.mm(boft_rotation, orig_weight)`, transposes back and multiplies by `boft_scale`. This problem mirrors those four fragments piece by piece.
- Paper: Liu et al., *Parameter-Efficient Orthogonal Finetuning via Butterfly Factorization*, arXiv:2311.06243 (ICLR 2024); its dense single-stage ancestor is the same authors' OFT, arXiv:2306.07280. Formulas and indices follow the source code.
- Two deliberate narrowings of the source, both written into the rules: first, peft's `boft_n_butterfly_factor` is 1-based (it subtracts 1 immediately, and value 1 makes the permutation return `torch.arange(n)`), while the problem's `F` is the true number of stages and equals dimension 0 of `boft_R`; second, in stage `i` peft uses the **floored** `int(boft_block_num / 2**i)`, so when `D` is not divisible by `2**i` the segment length `n // b` is no longer `H * 2**i` (e.g. `n=12, H=4, D=3`, stage 1 yields a single segment of length 12) — the problem rejects such configurations with `D % 2**(F-1) == 0`, which keeps the simplified rule "segment length `H * 2**i`, group size `H // 2"` valid everywhere. Also, peft only requires an even block size when the butterfly is enabled and allows odd `H` for `F = 1`; here `H` must always be a positive even number so that "the stage-0 permutation is the identity" needs no special case.

## Key ideas and pitfalls

**Only the skew part matters.** `S = (R - R.T) / 2` erases the symmetric part of `R` entirely, so adding any symmetric matrix to `R` leaves `Q`, `M` and `y` bit-for-bit unchanged (`check_only_skew_part_matters`). That is the whole point of the Cayley parametrization: an unconstrained square matrix stands in for the `H(H-1)/2` degrees of freedom of an orthogonal matrix, and the surplus symmetric entries are redundant.

**`left=False` is a right solve.** `torch.linalg.solve(A, B, left=False)` returns the `X` with `X @ A = B`, i.e. `Q = (I+S)^(-1) @ (I-S)`; the default left solve gives `(I-S) @ (I+S)^(-1)`. The two coincide for 2x2 skew matrices (both `I+S` and `I-S` are of the form `a*I + b*Ŝ`, hence commute), so a test suite restricted to `H = 2` **cannot catch this bug**; for general skew matrices of size `H >= 4` they differ, and `check_block_size_four` uses random 4x4 blocks precisely for that reason.

**`P_i` is a conjugation, not a left factor.** `M_i = P_i @ B_i @ P_i.T`: reorder the input axis with the butterfly, apply the block rotations in the reordered coordinates, reorder back. Writing `P_i @ B_i` alone still yields an orthogonal matrix but every block sits in the wrong place. The group size is `H // 2`, not `H`: a segment of length `H * 2**i` contains `2**(i+1)` groups and "even groups first, then odd groups" applies to those half-block groups — using `H` as the group size gives a different permutation (`check_block_size_four` pins the stage-1 permutation of `n=8, H=4` to `[0,1,4,5,2,3,6,7]`).

**Stage 0 is the identity permutation.** For `i = 0` the segment length is exactly `H` with only groups 0 and 1, so the order is unchanged and `M_0 = B_0` is strictly block diagonal (`check_single_stage_block_diagonal` verifies every off-diagonal block is zero and each diagonal block equals its Cayley result). The butterfly starts mixing at stage 1: with `F = 2, H = 2` the stage-1 permutation is `[0,2,1,3]` and the off-diagonal 2x2 blocks immediately become non-zero (`check_butterfly_mixes_blocks`).

**Order of the stage product.** `M = M_(F-1) @ ... @ M_0`, smaller stage indices on the right act first; peft's `for i in range(1, N): mat = batch[i] @ mat` is exactly this left-multiplying loop. The stages do not commute in general, so `check_stage_product_order` asserts both `M == M_1 @ M_0` and `M != M_0 @ M_1`.

**`M` acts on the input side of the weight.** `W' = (M @ W0.T).T` is `W0 @ M.T`: the rotation lives on the `d_in` axis, which is precisely why BOFT tolerates `d_in != d_out` (multiplying `M` into `W0` from the left fails the shape check immediately for non-square layers). Both equivalent spellings must hold — `check_rotation_on_input_side` re-verifies with `y = x @ M @ W0ᵀ` and asserts the `M @ W0` variant differs.

**`boft_s` is per output row.** Its shape is `(d_out, 1)` and it broadcasts after the transpose back to `(d_out, d_in)`, so it scales output neuron `r`; reading it as a per-input-column scale (shape `(1, d_in)`) or as a diagonal matrix multiplied from the left is wrong. `check_scale_applied_after_rotation` pins this from both sides ("enlarge one row only, the other rows stay bit-identical" and "scaling along the input axis gives a different result"), and `check_scale_orientation_shapes` uses the clean degenerate point `R = 0`, where `M = I` and `y` is just the base output scaled row-wise by `s`. Rotation and scaling **commute** (one acts on columns, the other on rows), so "rotate first, then scale" carries no numerical uniqueness; the statement fixes the source's weight layout as `W' = (M @ W0.T).T * s`.

**Orthogonality and norm preservation.** Every `Q` is orthogonal with `det = 1` and permutation matrices are orthogonal too, hence `M @ M.T = I` (`check_orthogonal_rotation`); with `W0 = I` and `s = 1` the forward pass is `y = x @ M` and each sample's 2-norm is unchanged (`check_norm_preserving`). With `R = 0` we get `S = 0` and `Q = I`, so the whole chain collapses to the identity (`check_zero_R_is_identity`) — that is peft's default initialization (`init_weights=True` zeroes `boft_R`), which means the adapter starts out as a no-op on the base model.

## How the judge cross-checks

- `_oracle` recomputes everything in plain numpy: `np.linalg.solve(eye + skew, eye - skew)` for the Cayley transform, Python loops that spell out `perm` as "segment -> even groups -> odd groups -> elements inside a group", an explicit `P[k, perm[k]] = 1` permutation matrix, `np.zeros((dim, dim))` slices for the block diagonal, and the running product `M = P @ B @ P.T @ M`. It shares no operator with the reference implementation.
- `check_against_oracle` covers 8 configurations (`F` from 1 to 3, `H` of both 2 and 4, including non-square layers, a bias, and pure float32 inputs) and compares both `M` and `y`; `check_example` pins the minimal case with a hand-derived 2x2 Cayley transform (`t = 2` gives `Q = 1/5 * [[-3,-4],[4,-3]]`).
- While authoring, the real library was used as a second opinion: `tuners.boft.layer.Linear(nn.Linear(in, out), 'd', boft_block_size=H, boft_n_butterfly_factor=F, boft_dropout=0.0)`, with `boft_R`/`boft_s` overwritten, compared against `solution.solve` on 10 `(in, out, H, F)` configurations (`F` up to 4, `in` up to 16): max deviation `2.9e-8` for `M` and `1.7e-7` for the forward pass (both pure float32 rounding of the returned tensors). Multi-stage cases require monkeypatching `FastBlockDiag` and `get_fbd_cuda`: when `get_fbd_cuda()` returns false, `update_layer` forces `boft_n_butterfly_factor` to 1 (warning "Setting boft_n_butterfly_factor to 1"), and the unpatched CPU branch uses `squeeze(0)` plus `torch.block_diag`, which is only correct for `N == 1`, i.e. a single stage. Also, `boft_P` is built with an unconditional `torch.empty(...)` in fp32 and `get_delta_weight` only moves it `.to(device)`, so a float64 comparison has to upcast it by hand. The single-stage path was additionally verified against unpatched peft on 6 configurations, within `1.2e-7`. The judge files never import peft.

## Complexity

Trainable parameters are `F * D * H * H + d_out` (versus `d_in²` for dense OFT): since `D * H = d_in`, that is `F * d_in * H + d_out`, i.e. linear in `d_in` with the constant hyperparameters block size `H` and stage count `F`. Materializing `M` costs `O(d_in²)` time and memory (the problem returns `M`, so the reference implementation takes this dense route: one `(d_in, d_in)` triple product per stage). Training need not materialize it: applying each `M_i = P_i B_i P_iᵀ` to a vector takes `D` block products of size `H×H` plus a reorder, `O(d_in * H)` time and `O(d_in)` space per stage, `O(F * d_in * H)` in total — that is why the paper uses the butterfly fast multiply. The forward `y = x @ W'.T` is still `O(N * d_in * d_out)`, the same order as the frozen base op, so what BOFT saves is optimizer state and gradient memory rather than forward compute.
