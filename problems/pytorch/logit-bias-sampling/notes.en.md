# Deep dive: Logit Bias and Banned Tokens

## Origin
- **llama.cpp (verified against the fetched source, item by item)**:
  - The assembly comment in `common/sampling.cpp` reads literally `// logit bias: user biases + model suppress tokens (-INFINITY)`: it copies `params.logit_bias` into a `merged` vector, then appends every suppress token from the vocabulary (`llama_vocab_get_suppress_tokens`) as `merged.push_back({ suppress[i], -INFINITY })`, and finally `samplers.push_back(llama_sampler_init_logit_bias(...))`. **The two steps become one sampler, pushed ahead of the dry/top-k/top-p/min-p/xtc/temperature block** — that is the basis for `llama-sampling-pipeline` recording bias as stage 0.
  - The body of `src/llama-sampler.cpp::llama_sampler_logit_bias_apply`: a fast path `if (lb.token >= 0 && cur_p->size > (size_t) lb.token && cur_p->data[lb.token].id == lb.token) cur_p->data[lb.token].logit += lb.bias;`, otherwise that entry goes into `to_search` and only a later linear scan matching `cur_p->data[i].id == lb.token` performs the `logit += lb.bias`. → the statement's "**additive**, entry by entry in map order, and **do nothing** when nothing matches" is a direct transcription of this code: out-of-range/negative ids neither raise an error nor get clamped.
  - Duplicate entries are **not merged**: the assembly only `push_back`'s and `apply` adds once per `lb`, so `[1,+0.5],[1,+1.5]` is `+2.0` (see trap 3).
  - In `common/arg.cpp`, `-l, --logit-bias`'s usage string is `TOKEN_ID(+/-)BIAS` (examples `--logit-bias 15043+1` / `15043-1`), and the `--ignore-eos` help text says outright `(implies --logit-bias EOS-inf)` → "banning a token" in llama.cpp *is* appending one more entry of `-INFINITY` to the bias map, which is exactly the relationship between steps ① and ② of the statement: one table, one special value.
- **OpenAI's `logit_bias`**: a token→bias map in Chat Completions whose documented convention is likewise **added to the logits before sampling**, with a stated range of \([-100, 100]\) and \(-100\) used to express "almost never pick this". `platform.openai.com` was unreachable from this judging environment (403), so the verbatim quote is **pending source verification (to be sourced)**; the difference from this problem is nevertheless a claim I can make about the **convention**: OpenAI offers only the additive channel, has no \(-\infty\), and a "ban" must be expressed as a sufficiently large finite negative number — see the counterexample in trap 1.
- **A dedicated `--banned-rp` style switch is not part of llama.cpp**: grepping `banned` in `common/arg.cpp` and `common/sampling.cpp` yields nothing, and hard suppression always goes through `logit_bias` with `-INFINITY` (suppress tokens / `--ignore-eos`). The `--banned-rp` mentioned in the authoring brief could not be located in the llama.cpp sources: **pending source verification** (it may come from another engine, so this problem only uses it as a generic label for "hard masking" and does not cite it).

## Full derivation and index conventions
Let \(V\) be the vocabulary size, \(\ell\in\mathbb R^{V}\) the original logits (with batching, each row is independent and the last dimension is the vocabulary), the bias map an ordered sequence of pairs \(\big((t_1,\delta_1),\dots,(t_n,\delta_n)\big)\) (repeats and out-of-range \(t_i\) allowed), and \(B\subseteq\{0,\dots,V-1\}\) the banned set.

1. **Bias.** For \(i=1..n\) in order,
   \[
   0\le t_i<V\ \Longrightarrow\ \ell_{t_i}\ \mathrel{+}=\ \delta_i,
   \qquad\text{otherwise skip that entry (no side effect whatsoever).}
   \]
   Closed form: \(\ell'_t=\ell_t+\sum_{i:\,t_i=t}\delta_i\), i.e. repeated indices **sum**; addition is therefore commutative and mergeable, but merging must be a sum — "take the maximum" or "last write wins" are both wrong.
2. **Mask.** \(\ell''_t=\begin{cases}-\infty, & t\in B\\ \ell'_t, & \text{otherwise}\end{cases}\) — an **assignment**, not anything else.
3. **softmax.** With \(M=\max_t \ell''_t\) (each row must have \(B\ne\) the full set, otherwise \(M=-\infty\) and \(\ell''-M\) is all \(\infty-\infty=\text{NaN}\); measured: `torch.softmax` on an all-\(-\infty\) row returns \([\text{nan},\text{nan},\text{nan}]\)):
   \[
   p_t=\frac{\exp(\ell''_t-M)}{\sum_{t'}\exp(\ell''_{t'}-M)},\qquad
   \exp(-\infty-M)=0\ \Longrightarrow\ p_t=0\ (t\in B)\ \text{holds exactly}.
   \]
   The denominator sums only the surviving terms, so \(p\) *is* "softmax over the surviving vocabulary". Two formulations agree up to float rounding: mask-then-softmax, versus softmax over everything then zero the banned entries and divide by the remaining mass — measured maximum absolute difference \(7.451\times10^{-9}\).
4. **Relation to "acting after softmax".** Adding \(\delta\) in the logit domain is identical to **multiplying** that entry's probability by \(e^{\delta}\) and renormalizing: with \(\delta=+0.5\) both routes give, to six decimals, \([0.366791, 0.366791, 0.134935, 0.081842, 0.04964]\) (max difference \(5.960\times10^{-8}\)). Treating the same number as an **addition in probability space** (\(p_1+0.5\), then renormalize) gives \([0.28577, 0.506662, 0.105129, 0.063764, 0.038675]\). This is the real meaning of "bias before versus after softmax": **multiply by \(e^\delta\)** is the correct reading, **add \(\delta\)** is not.
5. **Sampling.** \(\text{chosen}=\min\{t:\sum_{t'\le t}p_{t'}\ge u\}\) along the **original index order**; zero-mass banned entries create plateaus in the CDF, so "first index with cumulative \(\ge u\)" necessarily skips them. With vector \(u\) each row is independent (broadcast \(u\) to \((\dots,1)\) before the comparison).

The worked example step by step: \(\ell=[1.0,0.5,0.0,-0.5,-1.0]\), map \(((1,0.5),(1,1.5),(3,-2.0))\), \(B=\{4\}\), \(u=0.6\) → \(\ell''=[1.0,2.5,0.0,-2.5,-\infty]\), \(M=2.5\), \(p=[0.170075,0.762222,0.062567,0.005136,0.0]\), CDF \([0.170075,0.932297,0.994864,1.0,1.0]\) → first \(\ge0.6\) is index 1.

## Core traps
1. **"A large negative number ≠ \(-\infty\)" — this is the real trap of the problem**, and both layers must be stated:
   - *Numerics*: on the same \(\ell\), pushing index 4 down with a bias of \(-100\) leaves a post-softmax probability of \(2.802597\times10^{-45}\) (a float32 subnormal, **not** \(0\)); \(-30\) leaves \(5.76\times10^{-15}\), \(-16\) leaves \(6.930466\times10^{-9}\); only \(-\infty\) yields **exactly** \(0.0\). Curiously, in float32 the tail of the CDF is stuck at \(1.0\) in all three cases (a plateau), and scanning 200,000 values of \(u\) over \([0,0.999999999]\) never selected that position either — so the *sample* shows no difference, only the returned probability vector does (and `atol=1e-5` would not see that either). **Do not read this as evidence that "−100 is good enough".**
   - *Semantics*: an additive bias is a **relative** quantity — whether it "bans" depends on the **gap** between that token and the others, not on the literal size of the number. Measured counterexample: with \(\ell=[1000.0,0.0,0.0]\) and a \(-100\) bias on index 0 (the OpenAI-style "ban"), \(p=[1.0,0.0,0.0]\) — that token is still chosen with probability \(1\). Only the \(-\infty\) hard mask gives \(p=[0.0,0.5,0.5]\). Hence the ban in this problem must be a \(-\infty\) assignment.
   - The same logic applies to `masked_fill(torch.finfo.min)`: the collection's `causal-mask` / `llm-gqa-attention` already document \(-\infty\) and `finfo.min` as two different conventions, and this problem follows the \(-\infty\) branch.
2. **The bias is added to the logits, and the mask runs after the bias.** An index hit by both lists ends at \(-\infty\) (measured: index 4 gets `+50` first, then appears in `banned` → `biased_logits[4] = -inf`). Because the mask is an assignment and \(-\infty+\delta=-\infty\), swapping the two steps gives the same result in exact arithmetic — but the specified order is ①→②, so do not lean on that coincidence (with a finite stand-in for the mask, swapping genuinely changes the outcome).
3. **Repeated entries sum, they are not merged**: `[1,+0.5],[1,+1.5]` ⇒ `+2.0` (measured identical `biased_logits`). Building a dict with "last write wins" would yield \(+1.5\) — wrong.
4. **Out-of-range / negative indices are no-ops, not exceptions and not wrap-around**: the bias map \([-1,7,999]\) with \([5.0,-5.0,100.0]\) and banned \([-3,42]\) leaves a \(V=3\) input bit-identical to an empty map (measured). `clamp`-ing, taking `abs`, or letting an `IndexError` escape are all wrong.
5. **The softmax denominator is the surviving set**, not the whole vocabulary: banning index 0 of \(\ell=[5,4,3,2]\) gives \([0.0,0.665241,0.244728,0.090031]\) — the last three are exactly the softmax of \([4,3,2]\). Forgetting the renormalization leaves a row that does not sum to \(1\).
6. **A fully banned row is out of scope**: with \(M=-\infty\), `exp(-inf - (-inf)) = NaN` (measured), and the statement requires at least one survivor per row. `torch.softmax` handles a **single** \(-\infty\) entry perfectly (exactly \(0\)) but returns NaN for an **all** \(-\infty\) row, so switching APIs does not dodge this constraint.
7. **Do not mutate the input logits in place**: `biased_logits` is a new tensor (the reference clones first). Every problem in the collection that returns "modified logits" (`penalty-sampling`, `dry-sampling`) does the same.
8. **Batching and the shape of \(u\)**: with \((\dots,V)\) each row is independent and \(u\) may be a scalar, a single element, or shape \((\dots,)\); the inverse CDF must lift \(u\) to \((\dots,1)\) before comparing against the \((\dots,V)\) CDF — the reference does `u.view(u.shape + (1,)*(dim - u.dim()))` and uses `argmax` for the first \(\ge u\), falling back to \(V-1\) when nothing satisfies it.
9. **Do not use `torch.multinomial`**: the collection always hand-computes the CDF inverse transform, and the random number must be an explicit argument.

## Versus neighbouring problems
- **vs `penalty-sampling`**: the pair most easily conflated, since both "modify logits before softmax". Three layers of difference: ① **provenance** — penalties act on token counts **derived from the decoding history** (the n-gram `count` inside the `penalty_last_n` window) and change every step, while this problem's bias map is a **static, caller-named** list of (token, bias) pairs, history-free. ② **operator shape** — penalties first apply the sign-symmetric multiply/divide `l<=0 ? l*repeat : l/repeat`, then subtract `count*freq + (count>0)*present`; this problem is **pure addition** (a translation leaves the relative relations among all other tokens untouched and only changes the gap of that entry against the rest). ③ **output** — `penalty-sampling` explicitly does not sample and returns only the penalized logits, whereas this problem returns a triple and really draws once. Also, in llama.cpp these are **two stages** (the bias sampler is pushed into the chain first, penalties later), so the order is not a commutative optimization.
- **vs `dry-sampling`**: DRY punishes **continuations that repeat historical n-grams**, with a penalty that decays exponentially along the matched length, and converts a multiplicative base into an additive term; it is history-driven too and shares nothing with "name a token and shift its score".
- **vs the truncation/masking family (`top-p-sampling` / `min-p-sampling` / `xtc-sampling` / `top-n-sigma-sampling` / `typical-sampling`)**: those decide who drops out from the **shape of the distribution** (sort order, cumulative mass, ratio to the maximum probability, statistical thresholds), and the survivor set drifts step by step; here dropout is decided by **caller-named ids**, independent of how probable that token currently is — which is exactly why \(-100\) fails in trap 1.
- **vs banned / bad-words / grammar masking in general**: formally all of them are written as \(-\infty\), sharing "the support set is restricted". This problem's `banned` is that hard mask, deliberately distinguished from \(-100\)-style finite negatives; the difference is that grammar/structured-decoding masks **change with the generated prefix** (needing state and an automaton), whereas here the mask is a constant list supplied once.
- **vs `llama-sampling-pipeline` (in flight in the same batch)**: that problem puts bias at pipeline **stage 0** and then chains penalties→dry→top-k→top-p→min-p→xtc→temp; there, "bias before temperature" means the downstream temperature divides the offset by \(T\), so the effective probability factor is \(e^{\delta/T}\) rather than \(e^{\delta}\), and every stage must account for the survivor set. **This problem examines only the mathematics of the bias + ban step**: no temperature, no truncation, hence none of those ordering ambiguities, and no pipeline assembly is required.

## Cross-check design
The reference takes the tensor path: `clone` → entry-by-entry `+=` guarded by `0 <= tid < V` → write `NEG_INF` for hits in `banned` → hand-written softmax (`torch.where(torch.isinf(shifted), 0, exp(shifted))`, guaranteeing the banned entries are **exactly** \(0\)) → `cumsum` + `argmax` inverse transform. The judge's `_oracle` goes down a separate path: flatten logits into a Python list, `+=` entry by entry, use `None` as the \(-\infty\) sentinel for banned entries, get the shift from `max(x for x in lg if x is not None)`, do softmax with `math.exp` + `math.fsum`, and run the inverse transform as an explicit `acc >= uv` loop. Besides the example there are: 40 random full cross-checks (out-of-range and negative ids deliberately mixed into the bias map, \(0\sim2\) random bans), the equivalence of accumulating duplicates versus merging them, banned entries being exactly \(0\) while a scan of \(u\) never selects a banned position, out-of-range entries being bit-identical to an empty map, and the empty-map identity as a plain softmax including a \((3,6)\) batch. All compared with `allclose(atol=1e-5, rtol=1e-5)`, with the \(-\infty\) in `biased_logits` compared under `equal_nan` semantics.

## Complexity
Bias and mask cost \(O(n + |B|)\) each (per-entry lookup is constant-time here), softmax \(O(V)\), inverse transform \(O(V)\) (i.e. \(O(\text{rows}\cdot V)\) with batching). Space: one copy, \(O(V)\). In the C++ original the "fast path + linear fallback" double lookup exists to survive a shuffled candidate array; here the input is a full vocabulary vector, so direct indexing suffices.

## Practical notes
In production a bias map usually arrives from one of three places: a user's sensitive-word blocklist, forced prefixes for structured output (putting EOS at \(-\infty\) *is* `--ignore-eos`), or an agent framework saying "don't pick these tools this step". These need different semantics: the first two want a **true ban** (must be \(-\infty\)), the third usually only wants **down-weighting** (a finite bias). Writing all three as \(-100\) is a standard incident — either the ban leaks (see the \(\ell=[1000,0,0]\) counterexample in trap 1) or a down-weight silently becomes an elimination. Also remember the bias map is **resent every step**: carrying the same \(\delta\) at every step accumulates (tokens already generated get squeezed again and again), a bug invisible to single-step judging that only shows up end to end.
