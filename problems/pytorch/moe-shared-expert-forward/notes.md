# 参考做法：两条专家路径的直接合成

## 实现

共享专家和路由专家都是同一种 SwiGLU 映射，区别只在权重选择：

1. 对每个 token 用 `expert_ids` 取出 k 组 `[H,D]` 门/上投影和 `[D,H]` 下投影。
2. 路由输出按 `routing_weights` 加权求和，不重新归一化。
3. 共享专家用固定权重计算一次，直接相加，不乘门控。
4. 参数账按结构公式计算，不遍历实际张量求和去推断未给出的路由器。

可以用 `einsum` 一次处理 `[T,K,H,D]`，但只有 k 个专家参与前向。共享路径的隐藏宽度可以不同于路由专家，不能假设两者相同。

## 正确性检验

测试包含 14 个 `check_*`：手算示例、零路由系数、零共享下投影、系数不归一化、选中槽位置换、全专家、单专家、不同共享宽度、未选专家扰动、活跃参数不是 batch 并集、非连续输入、零输入、30 组随机标量 oracle、最大形状。

oracle 用纯 Python 标量循环逐元素重算 SwiGLU、加权和与参数账，不复用参考实现的张量广播路径。重点是 `active_params` 按每个 token 的结构路径计，而不是整个 batch 触达专家的并集。

## 范围与来源

机制对应 DeepSeek-V2/V3 中「共享专家始终激活 + 路由专家按系数合成」的公开设计，以及 Qwen 系列 MoE 的共享专家思路。本题只出**已给定的**路由结果，不实现路由器、不训练、不包含负载均衡损失或通信账。

共享路径采用**无额外门控**的 SwiGLU，区别于 Qwen2-MoE 等实现中的 sigmoid 门控共享专家；后者不在本题范围内。参数账只统计题面给出的专家矩阵，不应与整模型参数量或训练显存账混同。
